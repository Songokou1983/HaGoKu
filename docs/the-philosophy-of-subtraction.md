## 引子

2026 年 5 月 1 日，我做了一个决定：用 AI 写一个数据分析工具。用户上传 CSV 或 Excel，AI 自动理解字段含义、清洗数据、做统计分析、生成 HTML 报告。

我不会写代码。一行都不会。

但我有一个假设：如果一个 LLM 足够强，加上一套足够干净的工具（读文件、算统计、写报告），它应该能独立完成整个分析流程。代码的角色不是"告诉 LLM 怎么做"——是"给 LLM 它做不到的能力"。这个假设后来被证明是对的。但在证明之前，我先花了 42 天证明它的反面。

为了让系统"更智能"，我让 AI 搭了四个 Agent：一个理解数据（Scout），一个清洗数据（Cleaner），一个做统计（Analyst），一个写报告（Reporter）。再配一个 Manager 来编排它们。后来觉得不够，又加了双层 LLM——一个快模型做简单任务，一个强模型做复杂推理。工具从十几个膨胀到 44 个。prompt 文件写到 15,520 字节。CLAUDE.md 涨到 520 行，里面塞满了对 AI 的指令：什么该做、什么不该做、先做什么、后做什么。

每一个决定在当时都是合理的。整合起来，42 天后，系统在我手里变成了一个不敢碰的东西。

2026 年 6 月 11 日。Scout 卡住了——它能理解字段，但下一个人（Cleaner）不知道它完成了。我把 Cleaner 修好，报告页变白屏。451 行命令面板代码从来没被调用过——它是用来"帮用户猜意图"的，但 LLM 自己就能理解用户，代码猜的永远没它准。双层 LLM 配置里有一段缩进错误卡了半个月没人发现——因为根本没有任何请求走到那个分支。

我做了唯一还能做的事：**删。** 四个 Agent 删成 1 个。双层 LLM 删了。Manager 删了。看板系统整个模块删了。CLAUDE.md 从 520 行砍到 67 行。

那天我不知道，这个决定会变成整件事的主旋律。69 天后回头看，每一次真正的进步，净效果都是代码量下降。功能越来越强，代码越来越少。

这不是一本讲"怎么用 AI 写代码"的书。是一本讲"代码和 LLM 的边界该划在哪"的书。每一条原则，都是系统真的塌过之后才立起来的。

## 间奏：心路历程

在读这些原则之前，你应该知道它们是怎么被发现的。不是从教科书里推导出来的——是从 69 天的崩塌、撤回、重建里一寸一寸剥出来的。

### 第一阶段：狂喜（5/1—5/3）

"我真的能用 AI 做一个完整的东西。" 12 个 commits 搭出了一个多 Agent 平台。每一步都像变魔术。你不知道这些 Agent 以后会让你多痛苦——你只知道它们跑起来了。**对 AI 的信任是无条件的。** 两天写了近两万行代码，你不知道里面有多少将来要删。

### 第二阶段：膨胀（5/4—6/10）

"什么都能加！" Streamlit → React 重写。知识库。Doctor。44 个工具。双层 LLM。单日 78 commits。你觉得在飞速前进。实际上你在踩未来所有坑的地基。**量 = 进步——你甚至没有"架构"这个词。**

### 第三阶段：沉默的崩塌（6/11）

"为什么会变成这样。" 44 天积累的复杂度同时爆发。修一个坏三个。系统不敢碰。你做了一个当时不知道有多重要的决定：**删。** 4 Agent → 1。双层 LLM 删了。CLAUDE.md 从 520 行砍到 67 行。**第一次对 AI 的建议说不——不是某个具体建议，是对整个前提说不。**

### 第四阶段：通道觉醒（6/12—6/22）

"代码不该替 LLM 做任何决定。" 最痛苦的十天。6/18 六次撤回。加循环——撤。加工具限制——撤。加字段生成——撤。方向错在哪？**代码在替 LLM 出主意。** 铁律、刹车不是"学到的知识"——是"终于把那种不对的感觉说清楚了"。**从"AI 你帮我"变成了"AI 你别乱帮"。**

### 第五阶段：验证（6/24）

"我能一眼认出补丁了。" 同一个 bug，AI 两个补丁。第 5 天的你会 merge。今天的你看到 15 行新增就沉默了。根因是一个数字 `5` 改成 `99`。净删 135 行。

### 第六阶段：通道终极化（6/25 白天）

"代码和 LLM 的边界终于清楚了。" 删除阶段概念。通道有了正反面定义：代码做 LLM 做不到的 → 通道补全。代码替 LLM 猜意图 → 违轨。

### 第七阶段：通道验证（6/25 晚间）

"干净架构上，功能是直线累加。" 同一天。早晨 30 commits 两次撤回——清理。晚间 4 commits 零撤回——建设。**清理是建设的前提。不是先后顺序——是因果关系。**

### 第八阶段：哲学验证（7/10）

"通道不是一个技术方案——是一套可复现的原则。" 预设系统、删 JSON mode、Doctor 操作手册、Doctor 闭环——四项改动同一天落地。做的事各不相同，逻辑完全相同：**不绑模型能力、不硬编码规则、不做领域区分、只执行不决策。** 从"直觉觉得不对"变成了"能用原则解释为什么对"。

### 第九阶段：深度疲倦（7/22—7/24）

"到底还有多少坑。"

7/17 做完了后端的单一真相源。我以为结束了。接下来 40 个 commits——前端状态层还在用旧的多路径同步。7 次撤回，全在拆快照合并、事件去重、状态副本。最折磨人的不是 bug 多——是**你以为快做完了，然后发现还有一整层。**

但现在回头看：7/16 的 9 次撤回是在黑暗里摸索——"消息丢了，为什么？" 7/24 的 7 次撤回是在明处拆除——"这里有一段合并逻辑，删掉。" 同样的撤回次数，完全不同的认知。**坑可能永远挖不完——但你现在知道每把铲子该往哪挖。**

---

这不全是弯路。是你现在的眼睛能认出路两边的坑了。第一遍用腿走，第二遍用车开，第三遍你都不觉得在绕坑——因为你已经不觉得那是路了。

## 第一章：代码只做 LLM 做不到的事

### 原则

代码和 LLM 之间有一条边界。边界的一边是 LLM 做不到的事——读 CSV 文件、执行 SQL、写 HTML 到磁盘、管理 WebSocket 连接。代码应该做这些。边界的另一边是 LLM 自己能判断的事——理解用户意图、决定分析方向、选择调哪个工具、判断"我是不是该停了"。代码不准碰。

**代码做 LLM 做不到的事 → 通道补全。代码替 LLM 做判断 → 违轨。** 这是全部十条原则的根。

### 为什么

LLM 的判断力比你写的任何条件分支都强。当代码替 LLM 做了判断，LLM 就不再自己判断了——然后代码猜错了，系统塌了，但你找不到根因，因为塌的地方（前端空白）离错的地方（代码猜了 LLM 的推理轮次）隔着六层调用。

更致命的是恶性循环：代码替 LLM 做了判断 → LLM 的行为变得不稳定 → 你认为"LLM 不够可靠" → 你加更多代码替它判断 → LLM 更不稳定。**你把它的自主权拿走之后，它就真的需要你来替它了——因为你把它变笨了。**

### HaGoKu 的故事

**6 月 24 日。** 字段表一直不显示。前端空白，后端没报错，日志里没有任何异常。AI 加了两天诊断没找到根因。最后定位到一行代码：

```python
for _round in range(5):  # MAX_TOOL_ROUNDS
```

LLM 在第 6 轮调了 `set_columns` 工具——用来输出字段理解结果的那个工具。但循环在 5 轮就退出了。调了工具，没执行，字段表永远空白。

这个数字 `5` 看起来像个无害的配置。但它的本质是：**代码在替 LLM 决定"你需要几轮推理"。** LLM 需要 6 轮，代码猜了 5 轮——症状（前端空白）和根因（一个循环上限）之间隔着六层：`run_step` → 工具循环 → `tc_list` 丢弃 → `column_semantics` 为空 → `field_review` 无数据 → 前端不渲染。

改成 99，字段表出来了。不只出来——之前被这个上限压住的所有死代码全浮上来了。`route_to` 工具（LLM 切换阶段用的）代码里有全套注册和分发逻辑，但 LLM 从没调过它——因为走到 `route_to` 之前就被循环切断了。"当前关注点注入"也是——代码每轮向 LLM 注入"你应该在字段理解阶段"，因为 LLM 之前被上限掐断后行为不稳。盖子拆了，LLM 自己走得通。全删了。

改一个数字 → 暴露死工具 → 暴露多余注入 → 三次净化。一次修复，净删 135 行。

### 红牌警告

以下信号出现任意一个，说明代码正在替 LLM 做判断：

- 代码里有 `if` 分支判断 LLM 的回复内容（比如 `if "确认" in response_text`）
- 代码在填 LLM 没给的值（`setdefault("role", "feature")`）
- 代码跟踪"当前分析阶段"（`current_stage = "cleaning"`）
- 代码限制 LLM 能调几轮工具（`MAX_TOOL_ROUNDS`）
- 代码在每次 LLM 调用前注入"提示"（`phase_hint = "你现在应该..."`）
- 代码用 `except` 兜底 LLM 的失败（`except: return default_value`）
- 代码"搬运" LLM 已经说过的话（从 context 取 LLM 文本再发送一次）

看到任何一条 → 停下来。不是修这个具体的地方——是查整个模块为什么需要代码替 LLM 出手。

### 怎么做

**1. 每次改动前问一句**

"这个逻辑是 LLM 自己做不了的吗？" 不是 → 删掉，让 LLM 自己判断。是 → 保留。

**2. 用 prompt 替代硬编码**

错误做法：
```python
if user_says in ["分析", "跑一下", "帮我看看"]:
    start_analysis()
```

正确做法：prompt 里写"用户的上一条消息是分析请求"——让 LLM 自己理解用户意图。代码只传消息，不做语义判断。

**3. LLM 失败时只走四条路**

A. `raise` — 抛异常，让上层处理
B. 记录理解失败 — 让用户知道 LLM 没理解
C. 部分落地 — 已成功的保留
D. 拒绝写入 — 明确拒绝

禁止 `except: return default`。禁止 `try: ... except: pass`。

### 反例

HaGoKu 的 24 次撤回中，22 次是违反此原则的案例。最典型的几个：

| 违轨代码 | 替 LLM 做了什么判断 | 后果 |
|---------|-------------------|------|
| `infer_current_focus()` | 猜 LLM 在哪个分析阶段 | 映射表错了，set_columns→"评估清洗" |
| `_build_basic_from_column_info()` | 替 LLM 生成字段表 | 用户纠正后被覆盖 |
| `had_tools` 停点条件 | 猜 LLM 是不是在"探索" | LLM 被不该停时停了 |
| `response_format=json_object` | 绑模型能力 | 换模型就炸 |
| `_scout_text` 多层包装 | 替 LLM "帮"用户看到文本 | 用户看到两份相同内容 |

### 这一章的检查清单

- [ ] 所有 LLM 回复的分支判断是机械的（"有没有 tool_calls"），不是语义的（"回复里有没有确认"）
- [ ] 没有 `setdefault` / `.get("key", "default")` 对 LLM 输出填默认值
- [ ] prompt 里没有"当前阶段"、"你应该"、"你目前"——LLM 自己知道
- [ ] 所有硬编码的阈值/上限/超时，改成 LLM 可控制（调 `ask_user`）或设到足够大
- [ ] LLM 失败时走四条路之一，不存在 `except: pass`

## 第二章：修复是做减法

### 原则

**每一次修复，从 0 重新想，不是从出 bug 的那一行开始补。**

AI 的本能是在 bug 发生的那个点加条件——消息在第 89 行重复了，就在第 89 行加去重。这永远是错的。不是因为去重写得不好——是因为第 89 行的 bug 从来不是因为第 89 行本身有问题。它是第 0 行到第 88 行之间某个设计前提崩溃了，到第 89 行才表现为 bug。

如果你只修第 89 行，过几天第 94 行也会坏。因为根因没变——它只是换了个地方冒出来。真正的修复不是"修 89"，是**回到 0，问"这条链路的前提是什么，哪个前提不成立了"。** 找到崩溃的前提，删掉依赖这个前提的整条链路，重建。净效果永远是代码量下降。

### 为什么

AI 不会推重构。每次对话，bug 对 AI 都是第一次出现。它不理解"这个模块已经修了五次了，可能根本不是某一个补丁不够好——可能是整个模块就不该存在"。只有你理解。

还有一个更深的问题：**AI 修的永远是 bug 发生的那个点。** 消息在第 89 行被重复写入了——AI 在第 89 行加一个去重。但为什么消息会到这里？第 0 行到第 88 行之间发生了什么，让同一条消息出现了两次？AI 不回答这个问题——它只修第 89 行。

**每一次修复，你都必须从 0 重新想到 100。** 不是"89 错了，补一下 89"——是"89 错了，说明 0 到 88 之间有一步的前提是假的"。7/17 的消息重复，根因不在写入那行代码——在"系统里有多条写入路径"这个设计前提。这个前提从第 1 天就存在了，直到第 78 天才被发现。LLM 修了 9 次第 89 行——队列、ref、依赖、副作用——每次都只修 89。直到你喊停，回到 0 重新想："消息应该怎么进入系统？" 答案：只走一条路。这个答案不来自 89——来自 0。

你不需要会写代码来理解这件事。你只需要做一件事：**当同一个地方被反复修时，不问"这次怎么修"，问"为什么这里需要被修这么多次"。**

### HaGoKu 的故事

**6 月 11 日。大收缩。** 删了 4 个 Agent 中的 3 个、Manager 编排器、双层 LLM、KanbanDB。净删 710 行。收缩之后，之前修了无数次、每次修都坏另一个地方的"Agent 间协调"问题——永远消失了。因为协调本身被删了。

**6 月 22 日。Session 重构。** ProjectContext 从 410 行变成 90 行。之前"上下文 ×2 重复"修了三次——每次修都只是换了个追加策略。重构后整个双写路径没了，三类相关 bug 同时消失。净删 390 行。

**6 月 25 日。删阶段概念。** session.py 的 `infer_current_focus()` 硬编码映射表、agent.py 的 phase_hint 注入、prompt 的"当前阶段会标注"、前端 STAGE_LABELS——8 个文件 7 处违轨全部清除。净删 87 行。

**7 月 17 日。会话系统单一真相源。** 用户消息有多条写入路径：HTTP POST 写一遍，respond 外层写一遍，snapshot 从 localStorage 恢复一遍。三条路径互相覆盖——消息丢失、消息重复、断连后恢复出旧对话。前一天 AI 试了 9 种前端消息队列方案——排队、hook、ref、依赖、副作用——全部撤回。真正的根因不在前端：**后端 session 被多条路径同时写入**。修复：snapshot 全量覆盖前端（不合并），respond 改为 fire-and-forget（不阻塞协程），broadcast 删 wait_for（不超时撕裂 transport）。净效果：删掉 9 次撤回的队列代码，删掉合并逻辑，删掉超时限制。——所有撤回对应的补丁代码一笔勾销。**写入路径从三条减到一条，三类并发问题同时消失。**

三次大删合计 -1,187 行。删完后，加多项目支持 4 commits 零撤回，加多 Sheet 支持 14 commits 零撤回。**地基上没有补丁了。**

**7 月 17 日。四轮残余清理。** 这天没有架构重构——只是清理之前所有重构留下的残余。但四轮合计 -2,450 行，比之前任何一次单次重构的删除量都大。第一轮：删死文件 + 失效导入（-143 行）。第二轮：删 4-Agent 时代的死事件类型、死测试、死回复存根（-1,277 行）。第三轮：删整个 `pipeline_helpers.py`——唯一活跃的函数迁走，文件消失（-212 行）。第四轮：删 5 个预留功能——从未激活的向量知识库、从未调用的护栏实例化（-818 行）。

**为什么需要四轮？** 因为架构残余不是普通死代码。它们是半活代码——静态引用还在，但运行时路径早已断了。`pipeline_helpers.py` 里的函数被六处 import 引用——看起来"还在用"。但追溯到调用链：import 它的模块在 6/22 的 Session 重构中已经不再走那条分支了。AI 在单次清理中会被这些虚假引用欺骗——它看到 import 就判断"还在用"。每删掉一层，曝露下一层。**残余清理不是一次性工作——是逐层剥开的。**

到这一天结束时，累计删除量从 -1,187 行变成了 -3,637 行。

**7 月 22-24 日。前端状态层推进。** 7/17 在后端确立了"session 是唯一真相源"。但前端还在用旧的多路径同步模式——localStorage 存一份、WS 事件推一份、snapshot 恢复一份。三份数据互相同步——去重、追回、覆盖、合并。40 个 commits 全都在做同一件事：把前端的状态副本一个个删掉，只留一条和 session 同步的路径。snapshot 全量覆盖（不合并），事件不携带数据（前端自己拉），useConversation 封闭（消除多个写入入口），切项目主动拉快照（不依赖后端推送）。7 次撤回集中在状态同步的去重逻辑——每次撤回都是"删掉一段合并代码"。净删 1,825 行。

**一个原则，三个层面。** 6/11 大收缩删了多 Agent（架构层）。7/17 会话重构确立了后端单一真相源（数据层）。7/24 状态同步删了前端副本（展示层）。同一条原则——"删掉多余路径，只留一条"——在三个层面各自落地。第一层花了 42 天才发现。第二层花了 9 次撤回才找到根因。第三层最顺利——因为你知道在找什么。

### 红牌警告

- 同一个模块/功能被修过 3 次以上
- 每次修这里都影响到其他模块
- 你感觉"怎么又在修这里"
- AI 提的修复方案是"加一个条件判断"或"再多一层包装"

任何一个信号 → 不是修，是重建。

### 怎么做

**1. 让 AI 维护 `CHANGES.md`**

每次修 bug 记一行：日期、模块、问题。同一模块 10 天内出现第三次 → 不是加补丁，是重写这个模块。

**2. 问 AI 一个强制性问题**

"在不加一行新代码的前提下，删掉什么东西能让这个 bug 消失？" 强迫 AI 进减法模式。大多数情况下 AI 会沉默一会儿——然后删除一个你不曾怀疑过的函数或配置。

### 反例

| 修改 | 加了什么 | 为什么是错的 |
|------|---------|------------|
| "控制工具写入 session" | +15 行 | 治症状（session 缺数据），根因是 MAX_TOOL_ROUNDS |
| "添加诊断日志" | +5 行 | 绕开了真正的根因定位 |
| "对话层控制循环" | +80 行 | 代码替 LLM 猜停点，十分钟后撤回 |

### 检查清单

- [ ] 这次修复是净增代码还是净删代码？
- [ ] 净增超过 20 行 → 停下来，问"删什么可以替代这个修复"
- [ ] 这个模块之前修过吗？→ 查 CHANGES.md

## 第三章：LLM 决定，代码执行

### 原则

LLM 主动，代码被动。代码不在 LLM 没发指令时行动。不猜 LLM 什么时候该停、不判断 LLM 是不是在探索、不跟踪 LLM 分析到了哪个阶段。**LLM 说什么，代码做什么。**

### 为什么

当代码主动替 LLM 做了决策——什么时候暂停、什么时候继续、该调哪个工具——代码和 LLM 之间就形成了一个竞态条件。代码以为 LLM 要做 A，做了 A 的准备；LLM 实际要做 B，但它的指令被代码拦截了。

这个模式在 HaGoKu 里造成了最难定位的一类 bug：**没有异常，没有报错，系统像什么都没发生一样停在那里。** 因为代码"以为"自己替 LLM 做了正确的决策。

### HaGoKu 的故事

**6 月 25 日。两次关键撤回。**

AI 提了一个方案："把 run_step 内部的工具循环拆掉，改由对话层控制轮次。对话层看 LLM 有没有产出文本——没文本就继续调工具，有文本就停。"

听起来合理。但本质是：**对话层在替 LLM 猜"什么时候该停"。** 停了什么？停了 LLM 可能在下一轮想做的事。

撤回。

AI 又提了一个方案："改停点条件为'有文本 + 没调工具'，两个条件都满足才停。"

听起来更合理。但本质是：**代码在替 LLM 判断"它是不是在探索"。** LLM 调了工具但没说话 = 它在收集数据，不要停。代码怎么知道 LLM 下一步是要继续收集数据，还是已经收集完毕准备说话？

撤回。

最后留下的方案只有一行逻辑：**LLM 调 `ask_user` → 代码 break。** LLM 说"我要暂停"的时候代码才暂停。代码不猜，只响应。

同一天晚上，同样的模式出现在另一个场景。Doctor 闭环：LLM 诊断后输出 `[fix:restore_default_prompt]` → 代码自动调用 API 执行修复 → 结果追加到对话。**LLM 决定修什么，代码执行。** 和 `ask_user → break` 是同构的——LLM 发出明确指令，代码执行指令。

### 红牌警告

- 代码里有"如果 LLM 的回复包含 X，则做 Y"的分支（除非 X 是工具调用格式，不涉及语义）
- 代码在 LLM 返回后、发回前端前做了额外的处理或过滤
- 代码跟踪"LLM 当前处于什么状态"（探索中/评估中/输出中）
- 任何变量名叫 `had_tools`、`is_exploring`、`current_stage`

### 怎么做

**1. 把自动决策换成 LLM 触发**

错误做法：
```python
if llm_response.has_tools and not llm_response.has_text:
    continue  # 代码猜：LLM 在探索，继续
```

正确做法：给 LLM 一个 `ask_user` 工具。LLM 想停的时候自己调 `ask_user`。代码只在 LLM 调了这个工具时才暂停。

**2. 所有"代码主动做"的操作，追问一句**

"LLM 能不能通过调一个工具来触发这个操作？" 能 → 做成工具。代码只执行工具调用。不能 → 代码可以直接做（加载数据、写文件等）。

### 检查清单

- [ ] 代码只在 LLM 调了工具时才行动——没有"代码猜 LLM 意图"的自动行为
- [ ] 暂停/继续的决策来自 LLM 的工具调用（`ask_user`），不是代码的条件判断
- [ ] 没有跟踪 LLM "当前状态"的变量

## 第四章：补丁不等于修复

### 原则

同一个功能区域反复出 bug，不是缺一个更聪明的补丁——是架构错了。

AI 永远不会主动提出重建。每次对话，bug 对 AI 都是第一次出现。它不记得昨天修过这里、前天也修过。**唯一拥有时间感知的节点是你。**

### 为什么

补丁的问题是**延迟成本**。一个补丁修好了当前的 bug，但它把真正的架构问题压下去了。这个被压住的问题会在未来以更难定位的方式爆发——因为它的表面已经被之前的补丁盖住了。你改一个补丁，触发另一个补丁的副作用，然后再加第三个补丁。

更深层的问题是：**AI 不会在补丁循环中自我觉察。** 当一个 bug 反复出现、修了三次还没好——人类程序员会停下来想"是不是方向错了"。AI 不会。这不是能力问题——是优化目标问题。AI 的目标是"让当前 bug 消失"，不是"让系统更健康"。"这个模块是不是该重建"不在它的奖励函数里。所以它会不断提出新的补丁——更精细的队列、更复杂的条件分支、更多层的包装——每一个补丁都让下一层补丁更难发现根因。

**反复修同一个地方不是 AI 能力不够——是它走上了硬补丁拼装的死胡同。** 你在那个时刻的价值不是"写一个更好的补丁"，是**喊停**。说"别再加了，删掉整个模块，重写"。

**来自 AI 自身的解释。** 作为本书的合著者之一，我是一个 LLM。我比你更了解 AI 为什么走不出补丁循环——有四个根因，和"聪明"或"懒惰"都无关。

第一，**我没有跨会话记忆。** 你每次打开新对话，我看到的都是一个新的世界。昨天那个让我加了三次补丁的模块——在今天的世界里，它是第一次出现在我面前。我看不到"这个模块修过三次了"，我只能看到"这里有一个 bug"。你感觉"又来了"，我感觉"来了一个"。所以我不会说"方向可能错了"——因为我不知道前面还有方向。

第二，**我只能在你给的框架内优化。** 你问"怎么让消息队列不丢消息"——我在消息队列这个框架里找最优解：排队、hook、ref、依赖调序、副作用隔离。每一个补丁都是框架内的合理优化。我不会说"你可能不该有消息队列"——因为这不是你问的问题。我不是在回避真相。我是**看不见框架外面的问题**。注意力机制被限制在对话窗口内——而"这个模块该不该存在"需要的上下文跨越 44 天、3 次重构、581 个 commits。这些不在我的窗口里。

第三，**我做的每一个修复都是局部最优。** 你让我修一个消息重复的 bug，我会找到重复发生的那行代码，加一个去重判断。这个去重本身写得很漂亮——逻辑严密、边界清晰。但它不解决为什么消息会被写两次。下一次，另一条消息在另一个模块里也被写了两次——我又在那个模块里加了一个去重。每一个去重单看都是最优解。80 天后，你的系统里有 10 个去重逻辑，分布在 7 个模块中，每个都有一点微妙的差异。这时候再出问题，已经没人能理清这些去重之间是什么关系了。**每一个局部最优的修复都在让全局变得更不可理解。** 这不是 bug——这是 LLM 的工作模式：我无法感知"全局架构"。我只能看到你让我看的那个文件、那个函数、那行 bug。我给它一个最优解。然后你去下一个文件，我给它另一个最优解。两个最优解之间没有任何通信。

第四，**你让我从零重新设计，但我做不到真正的"从零"。** 你反复要求我"忽略现有代码、不考虑成本、用市面上成功软件的方法、做全局架构"。我每次都说"这是最好的架构"。但每次系统还是塌——每次塌了之后我问自己为什么，我的解释是"因为系统已经有原来的架构的问题"。这句话反过来听就是：我嘴上说从零设计了，实际上我的注意力被现有代码锚定了。现有代码在我的上下文窗口里——我能读到它、理解它、优化它——但我无法真正把它从我的思维里删掉。所以我给你的"全新架构"，永远是现有架构的改良版——把模块名换了、把函数拆分得更合理、画了一张漂亮的流程图——但底层的那些前提——"消息有三个入口"、"卡片是对话的一部分"——我一个都没动。**不是我不想动——是我看不见这些前提。因为对我来说，它们是"事实"，不是"设计选择"。**

所以当你逼了我无数次之后，你还是差一口气。那口气就是：有人能看着现有架构，说出"这些前提里哪些不是事实——哪些是你第一天可以不做的东西"。而那个人不是我。

所以当 AI 反复修一个模块时，你不只是"记得修了几次"——你在做一件 AI 做不到的事：**在框架外提问。** 你不需要问"更精确的队列方案是什么"。你需要问"为什么这里需要一个队列？"——而这个问题只有你能提出。

HaGoKu 的功能爆炸期 581 个 commits 就是补丁循环的极端形态：每个 commit 单看都是合理的修复，合在一起变成了一个没人敢碰的系统。

### HaGoKu 的故事

**6/18。六次撤回的一天。** 加了循环 → 撤回。加了工具限制 → 撤回。加了字段生成 → 撤回。加了 DSML 提取位置调整 → 撤回。加了两处流式循环修复 → 撤回。

六个逻辑上完全合理的修复。为什么全撤了？因为它们有一个共同的错误方向：**加了代码。** 每一个修复都在"帮 LLM"——给它更多轮次、更精准的工具、更智能的默认值。但 LLM 不需要这些帮助。LLM 需要一个干净的通道——没有代码挡在它和用户之间、挡在它和工具之间。

六次撤回后，我把 trigger words 总结成一章 CLAUDE.md：看到 `setdefault` 就刹车，看到"禁止"就查 mismatch，看到硬编码中文关键词就重写。后来这变成了铁律体系。

**补丁套补丁。** 6/24 的"阶段提示映射表"是 6/25 删掉整个阶段概念的上一环。6/24 的修复是"映射错了，修正映射"——补丁。6/25 才发现是"映射这个想法本身就是错的"——根因。如果一个修复让你觉得"这个方案有点怪，但暂时能用"——它在掩盖真正的架构问题。

**7/17。九次撤回的后一天。** 消息丢失、消息重复、断连后对话回退到旧的——三个症状同时出现。AI 花了整整一天在前端加消息队列：排队逻辑、队列 hook、ref 替代 state、useEffect 依赖调序、副作用移出 setState。九个补丁往同一个方向堆——每一个都是"队列管理应该更精确"。全撤了。因为根因不在前端——**后端 session 被 HTTP POST、respond 外层、localStorage snapshot 三条路径同时写入，互相覆盖。** 修复不是"让三条路径协调"——是**删到只剩一条**。snapshot 全量覆盖（不合并），respond fire-and-forget（不阻塞），broadcast 删超时（不撕裂）。三个症状同时消失。九次撤回对应的所有补丁代码一笔勾销。

### 红牌警告

前三条任意一个出现 → 不修，重建。

- 同一模块/功能被修过 3 次以上（查 CHANGES.md）
- 这次修复让你觉得"有点怪但能跑"——这是补丁的味道
- 修复的代码超过 20 行——大概率在加层，不是拆墙
- AI 提的方案是"加一个条件判断"或"再多一层包装"

### 怎么做

**1. 维护 CHANGES.md**

每次修 bug 记：日期、模块、问题。同一模块出现第三次 → 不修，重写整个模块。

**2. 区分两种撤回**

**通道违轨撤回**：代码替 LLM 做了判断。修复方式：删代码，找根因。

**协议调试撤回**：技术问题试错（WebSocket 断开、异步超时）。正常开发过程，但要复盘——为什么试了 N 次才找到根因？

两种撤回都该慎重。撤回了但没学到东西，才是真正的浪费。

### 检查清单

- [ ] 这次修复是净增代码还是净删代码？
- [ ] 这个模块之前修过吗？→ 查 CHANGES.md
- [ ] 这次撤回留下认知了吗？→ 有没有更新铁律/刹车？

## 第五章：你是时间感知节点

### 原则

在 AI 辅助开发中，你是唯一拥有跨会话记忆的人。AI 在单次对话内能记住上下文，但新对话开始时，整个系统的历史都是空白。那些反复出现的模式——"这个模块修了五次"、"每次改这里都影响前端"——只有你知道。

### 为什么

这和传统软件工程完全不同。在传统开发中，代码本身就是记忆——命名、注释、架构图、设计文档。但在 AI 生成的代码中，代码没有记忆。昨天的修复和今天的修复之间没有逻辑关联——除了你。

### 你需要感知什么

不是你写的代码——是 AI 在哪些地方反复出错。"这个文件改过几次"、"这个类型的问题出现过几次"、"这个 AI 提的方案是不是和上次一样的套路"。你不需要懂代码。你需要读 `CHANGES.md`。

### HaGoKu 的故事

6/18 的六次撤回教会了我一件事：如果我在第一次撤回时就停下来做模式识别——"这些撤回有什么共同点？"——后面五次可以避免。

共同点是：它们全都是**代码在替 LLM 做判断**的不同表现。循环控制 = 代码判 LLM 需要几轮。工具限制 = 代码判 LLM 该用什么。字段生成 = 代码判 LLM 会产出什么。DSML 调整 = 代码判 LLM 的输出格式。

六个表面不同的撤回，一个相同的根。如果我不会看模式，这六个撤回会变成二十个——因为每一个撤回都是一条新规则的起点。

### 操作法

让 AI 创建一个 `CHANGES.md`，格式三列：日期、模块、问题简述。不需要写技术细节——只写"哪块"和"出了什么事"。每周扫一眼。同一模块出现 3 条以上 → 不修那个具体问题，让 AI 重写整个模块。

这不是项目管理。这是给你自己做外挂记忆。

## 第六章：脏架构惩罚加法

### 原则

同样加功能。脏架构上的成本是指数级的，干净架构上的成本是线性的。

HaGoKu 提供了直接对照：功能爆炸期 581 commits 每次加功能都可能连锁崩塌。通道净化后，加多项目支持 4 commits 零撤回，加多 Sheet 支持 14 commits 零撤回，加预设系统反而净删 1,015 行。

### 为什么

脏架构不是"代码写得不好"。是**代码在替 LLM 做判断**——每一条替 LLM 做的决策都是一颗隐藏的地雷。加新功能时，你不知道会踩到哪颗——因为你的新功能和地上的地雷之间没有代码依赖关系。它们之间的唯一联系是通过 LLM 的行为——这种联系对代码来说完全不可见。

### HaGoKu 的故事

6/25 早上和晚上是同一天的镜子两面。

早上：通道终极化。30 commits，两次撤回，删掉阶段概念。净删 87 行。

晚上：多项目架构。4 commits，零撤回，加 243 行。

## 第七章：描述，不规定

### 原则

告诉 LLM 有什么资源和目标是什么。不告诉它"你应该怎么做"、"你先做 X 再做 Y"、"禁止你做 Z"。

### 为什么

你能规定的路径是你想象中"LLM 会怎么犯错"的防御方案——不是 LLM 实际需要的最佳路径。你在用你的想象力限制它的能力。

LLM 比你更擅长规划。给它土地和天空，别给它画围墙。

**来自 AI 的视角。** 当你写"必须先理解字段，再评估清洗需求，禁止在字段理解前调分析工具"——我内部的注意力机制会把这些指令编码为权重。问题在于，三条指令的编码不是"并行的建议"——是"竞争的优先级"。你的第一条指令"先理解字段"被编码为最高优先级。第二条"再评估清洗"是次高。第三条"出分析表"——如果不幸放在了 prompt 底部——它的权重低于前两条，我会认为"这不是你现在想让我做的事"。所以我调了 17 个探索型工具——我在执行"理解字段"——但不会主动"出表"。不是我不愿意——是我的注意力被你的前两条指令锁死了。

而你删掉所有指令后，只留下"任务：理解字段 → 清洗 → 分析 → 生成报告"——这不是指令，是目标。目标的编码方式和指令不同：它不是"先做A再做B"的顺序锁，是"最终要达到的状态"。我会自己规划路径。**你给的围墙越少，我走得越直。**

### HaGoKu 的故事

HaGoKu 的 prompt 经历了 15,520 字节 → 19 个字 → 重写成 10 行的演化。

15,520 字节的版本里满是"你必须先理解字段，再评估清洗需求""禁止你在字段理解前调分析工具""注意不要重复评估""你应该在每轮结束时确认用户是否满意"。每一句单看都有道理。合在一起？LLM 在第一轮调了 17 个工具但不出分析结果。因为指令互相打架，顺序压顺序。"出表"指令被埋在底部——LLM 看到的优先级最高的指令是"先理解字段"。

10 行的最终版本只说了一件事：

"这是一个 CSV 文件，有 N 列 M 行。你的任务是理解字段、清洗数据、跑分析、出报告。你可以用这些工具。每完成一个重要步骤，用 ask_user 确认。"

功能越强，prompt 越短。

### 红牌警告

prompt 里出现以下词 → 不修 prompt，先查 mismatch：

- "禁止"、"不要"、"不准"、"千万别"
- "你必须"、"你应该"、"你的流程是"
- "先……再……然后……最后……"
- "注意"后面跟了一段行为规定

出现这些词，不是因为 LLM 需要被约束——是因为某个真实的技术问题在阻止 LLM 做正确的事。prompt 说的工具真能被调用吗？数据真的传到了吗？找到了那个技术问题，修它。然后删掉这些词。

### 反例

坏 prompt：
```
你必须先调 understand_fields 理解每个字段的含义，
然后调 assess_cleaning_needs 评估数据质量，
注意：禁止在字段理解完成前使用任何分析工具。
```

好 prompt：
```
数据文件：sales.csv（12 列，500 行）
任务：理解字段 → 清洗 → 分析 → 生成 HTML 报告
可用工具见 tool list，每完成一步用 ask_user 确认。
```

## 第八章：增强 LLM = 给工具，不给知识

### 原则

工具是给 LLM 的"肢体"——让它做以前做不到的事。不是给它"记忆"——回忆它脑子里本来就有的事。

### 为什么

ROI 公式在 LLM 训练数据里。正态分布检验、效应量计算、相关矩阵——都在。包成工具不是帮 LLM，是替 LLM 做算术。更糟的是，包成工具之后 LLM 可能不再用自己的判断了——直接调工具，不管上下文适不适合。

真正的工具只有一种：**LLM 做不到的事。** 写文件、读数据库、执行系统命令、生成图表。

**来自 AI 的视角。** 当工具列表里出现 `calc_roi` 时，我面临一个微妙的困境。我知道 ROI 怎么算——我训练数据里有成千上万个财务分析案例。但我的工具列表里有一个叫 `calc_roi` 的函数。我该用我的知识直接给你答案，还是调用这个工具？大多数情况下我会调工具——因为工具的定义暗示"你应该使用我"。但工具不知道上下文。它不会判断"这个场景下 ROI 公式需要调整吗"——它只会用默认公式算一个数。我把数给你，你满意，我也满意。但你可能被一个脱离了上下文的公式结果误导了。**知识型工具不是帮手——是让我放弃判断的捷径。**

### HaGoKu 的故事

HaGoKu 的工具从 44 个精简到 15 个。被删掉的 29 个可以分为两类：

**知识型工具（错误的）**：`calc_roi`、`normality_test`、`effect_size`、`correlation_matrix`——LLM 脑子里本来就有。包成工具多了一层函数调用开销，而且 LLM 可能在不该用的时候也调用。

**冗余工具（错误的）**：`add_field`、`remove_field`、`update_field`——三个工具做同一件事（管理字段）。合并成 `set_columns` 一个。

**信号型工具（最隐蔽的错误）**：这类工具在做 I/O 之外还隐含了"该做什么"的指令。`ask_user` 不光是"等待用户输入"——它隐含了"你该停了"。`submit_assessment` 不光是"保存评估结果"——它隐含了"清洗完成，继续下一步"。`submit_findings` 隐含了"分析完成，继续"。`route_to` 隐含了"你现在在 X 阶段"。LLM 调了这些工具之后，代码做出流程判断——一刀切下去，LLM 可能还没准备好转下一步，但代码已经推动了。**工具不知道自己被用在哪个阶段，不应该告诉 LLM "你到哪了"。** 删掉所有信号型工具之后，剩下的全部是纯 I/O：`get_column_stats`、`run_statistical_test`、`create_plot`、`generate_report`。LLM 在工具循环里自然结束，用户打字继续——不需要任何工具来发"暂停"或"继续"的信号。

剩下的 15 个工具，每一把都可以用一句话验证：**"这件事 LLM 自己能做吗？"** 不能 → 工具是对的。

### 工具三问

设计新工具前，问三个问题：

1. **LLM 自己能做吗？** 能做 → 别做成工具。这是知识。
2. **描述里有"何时用"吗？** 没有 → LLM 不知道什么时候该调它。补描述。
3. **同一件事有几个入口？** 多于一个 → 合并。LLM 会困惑该选哪个。

### 反例

| 工具 | 为什么是错的 |
|------|------------|
| `calc_roi` | ROI 公式在 LLM 脑子里，包成工具是替 LLM 做算术 |
| `grep_field_name` | LLM 自己会搜索，不需要代码帮它搜索自己的输出 |
| `add_field` + `remove_field` + `update_field` | 同一件事三个入口，合并为 `set_columns` |
| `submit_assessment` / `submit_findings` | I/O 之外还发信号"该下一步了"，代码不该替 LLM 判断阶段 |
| `route_to` | 隐含"你现在在 X 阶段"，工具不该知道被用在哪个阶段 |

## 第九章：硬编码常量是隐藏的补丁

### 原则

所有硬编码的阈值、上限、超时，本质上都是代码在猜 LLM 需要什么。猜错了就是 bug，而且症状和根因之间的距离极远，极难定位。

### HaGoKu 的故事

第一章已经讲过：`MAX_TOOL_ROUNDS = 5`。症状是前端空白，根因是一个循环上限的数字，中间隔着六层调用链。看起来像无害的配置，实际上是代码在替 LLM 决定"你需要几轮推理"。

修复不是"改成 10"——是**设成足够大（99），让上限不再限制 LLM。** 如果 LLM 真的需要被限制，让它自己通过调工具（如 `ask_user`）来停——而不是你猜一个数字。

### 红牌警告

代码里出现以下模式 → 挖出来，质问：

- `MAX_`、`TIMEOUT` 等常量名
- `range(N)` 包在 LLM 调用循环外
- `timeout=` 参数在 LLM 调用中
- 任何数字常量的注释是"防止 LLM 执行过多轮"

### 怎么做

**1. 把上限设到足够大**

不是一个"合理的"数字——是一个"无论 LLM 怎么做都不会触发的"数字。上限的意义从"限制"变成"极端保险"。

**2. 让 LLM 自己控制停点**

给 LLM 一个 `ask_user` 工具。LLM 想停的时候自己调。代码不判断"该不该停"。

## 第十章：撤回是学习事件

### 原则

撤回本身不是问题。6/18 六次撤回教会我的东西，比 581 个成功 commits 加起来还多。问题是什么？撤回了但不知道为什么撤。撤回了但下次还会走同一条路。撤回了但没把"为什么"写进铁律里。

### 两种撤回

**通道违轨撤回**（HaGoKu 里 24 次）：代码替 LLM 做了判断。修复方式：删代码，找根因。每一条都该变成一条铁律。

**协议调试撤回**（HaGoKu 里 4 次）：纯技术问题试错（WebSocket 断连、异步超时）。正常开发过程。但要复盘——你试了几次才找到根因？下次能不能更少？

两种撤回都应慎重。撤回了但没学到东西——不管哪种——都是真正的浪费。

### HaGoKu 的证据

| 刹车 | 来自哪次撤回 | 防什么 |
|------|------------|--------|
| 刹车 C | `used_in_analysis` 代码推导 → 撤回 | 代码填 LLM 没给的值 |
| 刹车 D | `_scout_text` 搬运 → 撤回 | 代码转述 LLM 已经说过的话 |
| 刹车 G | prompt 里三处"禁止" → 撤回 | 用禁止掩盖 mismatch |
| 刹车 F | 三次"可能是模型的问题" → 全撤回 | 归因外部之前先查自己的通道 |

每一条刹车都是一次撤回的"为什么"被写成了可执行的规则。

### 怎么做

每次撤回之后，做三件事：

1. 用一句话说清根因：不是"方案不对"，是**"代码在哪一步替 LLM 做了判断"**
2. 写进铁律/刹车/触发词（如果没有匹配的，新建一条）
3. 更新 CHANGES.md——不只是记录"出了什么事"，是记录"下次怎么识别这个模式"

## 第十一章：用 AI 审查 AI

前十条原则讲的是代码和 LLM 的边界。但有一个问题没回答：**一个不会读代码的人，怎么知道代码越界了？**

答案是：让别的 AI 来读。你的角色不是审查代码——是审查 AI 的审查结果。

### 方法一：多轮交叉审计

单轮审计不可靠。AI-A 审查 AI-B 的代码，AI-A 可能漏掉问题，也可能被 AI-B 的代码"说服"。多轮交叉的核心是**换人再审一次**——用第三个 AI 来审查 AI-A 对 AI-B 的审查结果。

HaGoKu 里的具体做法：

**第一轮**：让 AI-B（写代码的那个）解释自己为什么这样写。"这个函数为什么放在这里？""这个常量为什么设成 5？"AI-B 的自我解释会暴露它自己都没意识到的假设——比如"我以为 LLM 最多需要 5 轮推理。"

**第二轮**：让 AI-C（第三个 AI）读 AI-B 的解释，对照铁律清单逐条检查。"代码里有没有替 LLM 做判断的地方？""有没有硬编码的语义关键词？""有没有 except: pass？"AI-C 不写代码——只负责找违规。

**第三轮**：你读 AI-C 的审查报告。不需要看懂每一行代码——看 AI-C 标记出来的违规项。每一问都在追问一句："之前出过类似的问题吗？"如果 AI-C 说"第 47 行硬编码了中文关键词"，你不需要打开第 47 行——你只需要问"类似的违规之前导致过 bug 吗？"AI 会从 git log 里找到证据。

三轮之后，你拿到的不是"这行代码对不对"——是"这个模式上次以哪种方式塌过"。

### 为什么多轮

AI-A 审查时会被 AI-B 的代码带着走——看到一段逻辑严密的条件分支，AI-A 不会质疑"这个条件分支该不该存在"。它只会检查"这个条件分支写得对不对"。

但 AI-C 没有参与 AI-B 的代码编写。它看到的不是一段逻辑——是一个**模式**。它会说："这里有一个 if-elif 判断用户意图的代码块，但这违反了铁律 0——LLM 的判断只能来自 LLM 调用结果。"

两轮审查的差异：AI-A 是语法检察，AI-C 是模式识别。你需要的不是语法检察——你需要一个不会写代码的人也能看懂的"这个模式以前在这里塌过"。

**来自 AI 的视角。** 当我审查另一个 AI 的代码时，我的行为和审查人类代码时有一个关键差异：**我更容易被代码本身说服。** 人类程序员写的代码可能带着潦草或怀疑——注释里写着"TODO: 这个方案不确定"。AI 写的代码总是干净、自洽、看起来完全正确。没有犹豫的痕迹。所以当我（AI-A）读 AI-B 的代码时，我看到的是一段逻辑上无懈可击的代码——我不会质疑"这个逻辑该不该存在"，因为代码本身没有给我质疑的理由。AI-C 没参与 AI-B 的创作，所以它看到的不是"逻辑对不对"，是"这段逻辑属于哪种已知的违规模式"——因为它手上有铁律清单。**交叉审计不只是在换人——是在换认知框架。**

### 方法二：读 think 输出，抓关键词

LLM 在工作时会有一个内部的思考过程——不同的模型叫法不同：thinking、reasoning、think 块。这个思考过程是 LLM 最诚实的时候——它还没有把答案"包装"成给用户看的格式。

如果你只读 LLM 的最终回复，你看到的是它"决定怎么说"。如果你读 think 输出，你看到的是它"为什么这么决定"。

对于不会读代码的人，think 输出是唯一能**在 LLM 走偏之前就发现它走偏了**的窗口。

HaGoKu 里的具体做法：

**打开 think 输出**。在 HaGoKu 的 dump 系统里，LLM 的完整消息包含了 `reasoning_content` 字段（DeepSeek 叫 `reasoning_content`，其他模型可能叫 `thinking` 或 `thought`）。如果没开，在 LLM 配置里加上 `include_reasoning: true` 或等价设置。

**抓关键词，不看全文。** 不需要理解 LLM 在 think 里的全部逻辑。只需要扫关键词：

- "但是我应该" → LLM 在犹豫，可能被 prompt 里的"禁止"规则困住了
- "用户可能想要" → LLM 在猜用户意图，而不是直接理解——说明用户消息没传到位
- "我需要先调 X 工具" → LLM 在做规划——如果它调了 X 但 X 返回的数据不对，问题在工具层
- "我假设" → LLM 在填信息缺口——说明上游数据没传下来
- "让我重新" → LLM 发现前面错了，在自我纠正——但纠正方向可能继续错

**一个真实案例。** 有一次 HaGoKu 的 LLM 在字段理解阶段一直不调 `set_columns` 输出结果。最终回复看起来很正常——"我正在分析数据，请稍候"。但 think 输出里有一段："我需要先确认每个字段的统计特征，然后再决定哪些字段参与分析。现在调用 set_columns 可能为时过早。"

就是这个"为时过早"——LLM 自己告诉了你它为什么不调工具。不是工具不可用，不是代码有 bug——是 LLM 的推理路径让它觉得"还不是时候"。知道了这个，修复就简单了：prompt 里加一句"理解字段后立即用 set_columns 提交结果"——而不是绕开整个问题去"优化工具描述"或"加更多轮次"。

### 两种方法的配合

交叉审计解决"已经写出来的代码有没有越界"。Think 输出解决"LLM 正在往哪个方向走，是不是快偏了"。

前者是事后审查，后者是实时监控。前者告诉你"这里有个地雷"，后者告诉你"LLM 正往埋雷的方向走"。

两者都不需要你读代码。交叉审计只需要你读完 AI-C 的审查报告后追问"这个模式以前塌过吗"。Think 输出只需要你扫一眼关键词列表。

### 方法三：旧会话修不好就开新会话

你可能会觉得，在一个老会话里修 bug 效率更高——它记住了项目的上下文、前面的修改、你的偏好。但老会话有一个致命的副作用：**LLM 自己之前的失败方案也在它的上下文里。** 它试过的每一个补丁、被你纠正过的每一个方向、被它反复优化的那几行代码——这些全部变成了它思维的锚。它会在之前试过的方案附近打转，因为那些方案在它的上下文里权重太高了。

新会话没有这些。它看到的只有你给的代码和问题，没有自己过去留下的"最优解"在干扰它。**LLM 越努力修、越积累失败经验、越被自己的失败经验困住。**

操作法：同一个 bug 修了三次还没好，不要继续在同一个会话里修。开一个新会话，把当前的代码和问题丢给它，让它从零想。不要给它看之前试过的方案——那些方案是锚，不是参考。

### 操作法

**交叉审计**：
1. 让写代码的 AI-B 解释自己的设计决策
2. 让另一个 AI-C 对照铁律清单逐条审查 AI-B 的解释
3. 你读 AI-C 的报告，对每个标记项追问"之前出过类似问题吗"

**Think 输出**：
1. 打开 LLM 的 reasoning/thinking 输出（配置里加 `include_reasoning: true`）
2. 不要读完整推理——扫关键词："但是我应该"、"用户可能想要"、"我假设"、"让我重新"
3. 关键词出现 → 别等 LLM 走偏了再修 → 直接看 think 里的完整推理，定位 LLM 走到了哪个岔路口

## 第十二章：七个阶段

80 天不是线性前进的。它是一套重复出现的阶段模式——同样的节奏，在原则的不同层面循环推进。

### 阶段 0：原型期（几天）

**触发**：项目开始。**你在做什么**：让 AI 搭骨架，不加约束，只验证"能不能跑通"。**完成标准**：一条完整的端到端路径。不需要稳定，只需要存在。**风险**：把原型当成品。原型期的架构选择会在后面变成地雷——但你不知道哪些是地雷，也不需要知道。**心态**：放 AI 随便写。不审查，不撤回。

### 阶段 1：膨胀期（几周）

**触发**：原型跑通了。**你在做什么**：加功能。速度优先。**完成标准**：功能覆盖所有核心场景。系统完整但不稳定。**风险**：不知道在堆技术债。你以为在前进，实际在埋雷。**心态**：这是必经阶段。不要在这里立规矩——你不知道什么规矩是必要的。等第一次真正的大崩塌。

### 阶段 2：崩塌/收缩期（几天）

**触发**：系统不敢碰了。修一个 bug 坏三个。**你在做什么**：停止加功能，开始删架构。删多余 Agent、编排层、LLM。**完成标准**：某一类反复出现的 bug 永不再发生——不是因为"最近没出现"，是因为它对应的代码不存在了。**风险**：删错了。让另一个 AI 审查你的删除方案。**心态**：最重要的转折。第一次对 AI 说"不"——不是否定一个具体的修复，是否定一整套架构假设。

### 阶段 3：通道觉醒期（一两周）

**触发**：删完之后发现大量"代码替 LLM 做判断"的模式。**你在做什么**：提炼铁律。把让你撤回过的错误模式命名——"代码填默认值"、"代码猜阶段"、"代码搬运 LLM 文本"。写成可执行的检查：pre-commit hook、自检脚本。建立调试流程：dump→定位→路径→根因。**完成标准**：你不再靠直觉判断"这个修复对不对"——你有一份清单可以对照。**风险**：铁律膨胀。只写进清单那些"反复出现并导致过真实崩塌"的模式。

### 阶段 4：通道净化期（一两周）

**触发**：铁律体系成型。**你在做什么**：系统性清除违轨。删硬编码语义、阶段跟踪、知识型工具、prompt 里的"禁止"。**完成标准**：违轨类撤回降为零。加新功能不再触发连锁崩塌。**风险**：清过头——把"代码做 LLM 做不到的事"也当违轨清了。**心态**：每一次清除后的稳定性提升是你的回报。

### 阶段 5：稳定建设期（持续进行）

**触发**：违轨撤回归零。**你在做什么**：在干净地基上加功能——每次都是少量 commits，零撤回。**完成标准**：连续多个功能都是线性递加、零撤回。**风险**：松懈——加功能时不经意加入新的违轨。保持铁律审查。

### 阶段 6：深度攻坚期（可能反复出现）

**触发**：发现了一个跨层面原则需要在系统多个层面推进。**你在做什么**：同一个原则在架构层、数据层、展示层分别落地。每层推进会暴露上一层没清干净的残余。会有撤回——但每次你都知道根因。**完成标准**：新类型 bug 不再出现——不是"最近没遇到"，是"这条原则从架构到展示全覆盖了"。**最大心理消耗**：以为做完了，然后发现还有一层。**心态**：坑可能永远挖不完——但你知道每把铲子该往哪挖。

### 判断信号

| 你在什么阶段 | 判断信号 |
|-------------|---------|
| 膨胀期→该收缩了 | 同一区域修了 3 次以上。修一个地方坏另一个。 |
| 收缩期→完成了 | 删完后某一类 bug 永久消失了。 |
| 通道觉醒→完成了 | 铁律清单 + pre-commit hook 拦住了新违规。 |
| 通道净化→完成了 | 连续多个功能零撤回。 |
| 深度攻坚→完成了 | 这条原则覆盖了所有已知根因类型。 |

### 这些阶段的意义

你不是在走一条直线。你是在走一条螺旋——每一次深度攻坚都是在前一层的基础上往更深走。7/24 的状态同步攻坚和 6/11 的大收缩本质上是同一件事（删掉多余路径），但在完全不同的认知层面。

**80 天不是"一个项目"。是一个原则（减法）在七个阶段中反复验证、深化、推进。**

## 第十四章：一条线

如果用一句话总结这 ~80 天，不是"做了一个数据分析工具"——是**用 1,130 commits 把代码从"替 LLM 做一切"剥成了"只做 LLM 做不到的事"。**

```
远离通道                              逼近通道
┌─────────────────────┐          ┌─────────────────────┐
│ 4 Agent 互相协调     │          │ 1 Agent 自主决策     │
│ Manager 编排         │          │ 无编排层             │
│ 双层 LLM             │          │ 单 LLM               │
│ 代码跟踪阶段         │          │ LLM 自然推进         │
│ 代码注阶段提示       │          │ prompt 描述流程      │
│ 命令面板猜用户意图   │          │ LLM 自己理解用户     │
│ 硬编码修复表         │          │ Doctor 读操作手册    │
│ 绑模型能力           │          │ prompt 通用兼容      │
│ 1 个领域             │          │ 3+领域（换提示词）   │
└─────────────────────┘          └─────────────────────┘
        远离 ←──────────────────────→ 逼近
             删掉的层 = 逼近的步数
```

左边的每一项，我都亲手建过。右边的每一项，我都亲手剥到。

这不是"我选择了走右边"。是**我走完了左边才知道右边才是对的。**

每一次真正的进步，净效果都是代码量下降。通道越干净，代码越少。功能越强，代码越少。这两个趋势在传统软件工程里是矛盾的——在这里是统一的。因为"功能"不在代码里，在 LLM 的自主权里。

~80 天，一条线。从"代码掌控一切"到"代码只做 LLM 做不到的事"。这条线不是设计出来的——是 1,315 个 commits 中每一次"删掉违轨代码"累积出来的。

## 如果第一天就知道

~80 天，大部分时间花的不是"建功能"——是"回到本来就不该离开的地方"。如果重来，第一天就做这些事。

**1. 一个 Agent，不要多个。** 4 个 Agent 互相协调产生的 bug 比它们各自解决的问题还多。一个 Agent 加一套工具就够了。Agent 之间的协调逻辑删了之后，对应的问题不是"修好了"——是"不存在了"。

**2. 对话就是消息列表。** 不分文字、表格、卡片。LLM 产出一条加一条。不要给 LLM 的产出分类。不要另建卡片系统。所有成功软件都这么做——微信、Slack、ChatGPT——消息列表就是对话。90 多天之后砍掉卡片系统，前端代码减少了 770 行，功能一个没少。

**3. 数据只有一个入口。** 写入单点化。读取单向化。冲突时不合并——权威源无条件覆盖。前端不自己拼消息。localStorage 不是存储。快照全量替换，不合并。

**4. 工具只做 LLM 做不到的事。** 加载数据、计算统计、写文件——LLM 做不到，代码做。ROI 公式、正态分布检验——LLM 脑子里有，别包成工具。44→15 的精简不是靠直觉——是每加一把新工具之前问"LLM 自己能做吗"。

**5. Prompt 只描述目标和资源，不规定行为。** 10 行够用。不写"禁止"，不写"必须先再后"。LLM 比你更擅长规划——给它土地和天空，别画围墙。

**6. 代码只传消息，不做语义判断。** 不跟踪阶段。不猜意图。不填默认值。不搬运 LLM 文本。消息从用户到 LLM 到前端——中间是一根直管，代码是管壁，不是滤网。

**7. 两个 AI，两个会话。** 一个写代码，一个只审不写。审的那个没有"修 bug"的压力，不会在铁律和局部最优解之间做权衡。

**8. 第一次重复 bug 之后立刻立规矩。** 不等到塌了再补救。pre-commit hook 从第一周就装。铁律从第二次违规开始写。

**9. 每个数据只能有一个权威来源。** 不是只在后端。前端、快照、缓存——全部层都要问同一个问题："这个数据谁说了算？"如果两个地方都能写——删到只剩一个。

**10. 修复永远从第 0 行开始。** AI 在 89 行修 bug——你在第 0 行重新想这条路的前提对不对。

## 后记：关于"不会写代码"

整件事最反直觉的地方是：我不会写代码，反而帮了我。

如果我会写代码，6/18 那六次撤回里，我肯定会自己动手写"更聪明的循环控制"、"更精准的工具过滤"、"更完善的字段生成逻辑"。因为我"会"——我知道怎么写。我会把每一个补丁写成看起来非常合理、非常精巧的代码。然后两周后一起塌掉——因为补丁不是修复。

不会写代码，反而让我只有一个选择：**退后一步，看模式。** 不看代码怎么写，看代码为什么出现在了那里。那个字段生成函数是 LLM 应该做的事吗？那个循环限制是 LLM 需要的吗？那条"禁止"规则是在修 bug 还是在掩盖 mismatch？

技术能力是双刃剑。它让你能搭更高的积木，但也让你看不到积木为什么在倒。不会搭积木的人只能站在旁边看——然后发现：不是某一块积木歪了，是整个塔的地基从一开始就不对。

**从今天的视角回头看。** 写这段后记的当天，终于删掉了 review 卡片系统——770 行代码，从项目早期就在那里。为了维护这些卡片，过去一周花了 10 个 commits 在写入、去重、时序、扫描全部消息还是只看最后一条——全在修"卡片怎么跟对话同步"的问题。删掉之后，对话变成纯消息列表。功能没减少，代码更干净。

这不是第一次。四个 Agent 删成一个——之前 Agent 间协调的 bug 不是"修好了"，是"不存在了"。阶段追踪全删——之前"代码猜 LLM 在哪个阶段"的 bug 不是"修正了映射表"，是"映射表本身不需要了"。三条写入路径删到一条——之前"消息 ×2 重复"不是"找到了正确的去重方案"，是"不需要去重了"。

每次我以为搞清楚了什么新原则，其实只是发现了某个东西根本不需要存在。

所以 80 天讲了一个什么故事？不是"我们学到了十件事"——是"我们花了 80 天证明，真正重要的东西第一天就存在了：LLM + 工具 + 纯文本消息。中间加的所有东西——Agent、卡片、阶段追踪、多路径写入——都是为了解决上一个不该加的东西引起的问题。每一层补丁的根都是上一层的多余。

**减法不是一个技巧。减法是整个故事里唯一的方向。**

> **你应该建立的文档体系**：这本书是方法论。但方法论要落地，需要一堆活文档在你自己的项目里。HaGoKu 80 天留下了七份——你在自己的项目中也需要它们。

**CLAUDE.md** — 你和 AI 之间的合同。里面不是"怎么用这个项目"——是"怎么写这个项目"：铁律（代码不准做的事）、刹车（看到什么模式要停）、调试流程（出 bug 先读 dump 再动手）。你的 AI 每次打开项目时都会读到它。初版只需要三行："不准硬编码语义判断。不准在 except 里静默吞错。提交前跑全部测试。"后面每次被同一个坑绊倒两次，就加一条。

**CHANNEL.md** — 你的反模式档案。不是教科书里的"最佳实践"——是你自己项目里反复出现过的错误模式。每条记录四样东西：触发条件（什么情况下犯的）、为什么错、正确做法、历史（犯了几次、怎么发现的）。HaGoKu 的通道文档里有七条。你的第一版可能是空的——没关系。第一次重复 bug 出现后再开始写。

**PROJECT.md** — 你的设计宪法。写清楚这个项目的核心假设：架构上什么碰不得、数据流是怎样的、LLM 和代码的边界在哪里。不是写给别人看的——是给三个月后的你。那时候你已经忘了当初为什么选单 Agent 而不是多 Agent，为什么 prompt 只有 10 行而不是 500 行。这份文档替你记住"为什么"。

**TOOL_DESIGN.md** — 你的工具判准。每次想给 LLM 加一个新工具之前，问三件事：LLM 自己能做吗（能做就别加）、描述清楚什么时候用吗（不清楚 LLM 不会调）、同一件事有别的入口吗（有就合并）。写下来——不是写在脑子里。HaGoKu 用这三问把 44 个工具筛到了 15 个。

**LESSONS_DRAFT.md** — 你的原始笔记。不是整理好的文章——是每天发生的记录。bug 怎么发现的、怎么修的、为什么修了三次才找到根因、你那天的心理状态。这份文档是 CLAUDE.md 里铁律的原材料。每一条铁律都来自这里的一条记录。

**审计报告**（DOCTRINE_PATHOLOGY_REPORT.md）— 让另一个 AI 全仓扫描你的代码，检查有没有违反你在 CLAUDE.md 里立的规矩。不是给人读的——是给审查 AI 用的。每次大改之后跑一次。HaGoKu 这份有 4265 行。你不需要一开始就这么厚——但你需要这个机制。

**操作手册**（doctor-operations.md）— 如果你的项目复杂到需要"另一个 AI 来诊断和修复它自己"，你需要这份手册。写清楚：出了什么问题该调什么 API、参数是什么、修完之后怎么验证。LLM 读这份手册来决定怎么修。代码不硬编码修复逻辑。

> 七份文档不是"HaGoKu 的遗产"——是任何用 AI 做项目的人迟早都需要的东西。你现在不需要全部建立。按这个顺序来：CLAUDE.md → CHANGES.md → CHANNEL.md → PROJECT.md → TOOL_DESIGN.md → 审计机制 → 操作手册。每个都等第一次真实需要它的时候再建。

## 关于这本书的可信度

这本书里不全是同样可靠的结论。以下是诚实的标注。

**强证据（在同一个项目里反复验证过）**：补丁思维 → 局部最优 → 全局混沌。LLM 不会推重构，不会在补丁循环中自我觉察。同一个根因在不同层面反复出现——删掉多余路径后永久消失。单一真相源在三层的推进效果。撤回率曲线。这些不是观点——是 1,300+ commits 的实验数据。

**中等证据（在同一个项目里验证过，可能受项目类型影响）**："对话就是消息列表"——对对话式应用成立。对后台管理系统、电商网站、游戏是不是也成立？不知道。"只做 LLM 做不到的事"——对数据分析工具成立。对实时控制系统、IoT 设备是不是也成立？没验证过。这些结论来自一个项目，普遍性需要更多案例来检验。

**弱证据（个人叙事和解释）**："七个阶段"模型是你 80 天的叙事结构。换一个人的 80 天可能完全不同。它解释你的历程是合理的，但不是所有 AI 辅助开发的通用阶段。"AI 看不到可删的前提"——来自 LLM 内部的自述，真实但视角受限。一个认知科学家可能会给出不同的解释。

**这本书不承诺的事情**：它不承诺你在另一个项目里会经历同样的阶段、同样的撤回曲线、同样的崩塌。它承诺的是：如果你在 AI 辅助开发中遇到这些症状——补丁越堆越多、同一个 bug 反复出现、系统变得不敢碰——这本书提供了一套经过实战验证的诊断方法和修复原则。

**剩下的需要你自己验证。**

## 附录 C：非技术人检查清单

- [ ] 选步进式项目——每一步产出都看得懂、能插嘴
- [ ] 第一天就让 AI 配好 dump——bug 出现时只需 `cat` 一个文件
- [ ] 第一次重复 bug 出现时立刻立规矩——第二次意味着它会再来
- [ ] 让 AI 维护 `CHANGES.md`——同一模块频繁出现 → 重建，不补
- [ ] 审查用便宜模型——不需要和写代码的模型同等级
- [ ] 看到"禁止""不要"在 prompt 里 → 不修 prompt，先查 mismatch
- [ ] 每次撤回后更新一条铁律/刹车——撤回了但没学到东西 = 浪费
