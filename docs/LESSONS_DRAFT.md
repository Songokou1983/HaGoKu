> ⚠️ 这是 2026-06-22 的对话中提炼的初稿。项目还在进行中，可能有过时的、不准确的、遗漏的。等项目收尾后再回头看、修改、定稿。
>
> 本稿经 AI 评估修正。关键修正：措辞从绝对化改为精确化（"三次"→"重复性"、"速成"→"无全局视角"）；补充了三个缺失的边界条件（版本控制、领域知识、模型能力）。

## 给未入门的人

1. **选步进式项目，别选一次性生成** — 每一步产出你都能看懂、都能插嘴。对话式是步进式的一种，分段生成也是。核心：中间状态可见。

2. **唯一需要学的能力：读 dump** — 三问定位法：用户最后说了什么？LLM 回了什么？工具调用了吗？**第一天就让 AI 帮你配好 dump，你只需要 `cat` 一个文件。** 不要自己配置。

3. **两个 AI 互审，你做裁判** — 不需要懂代码，需要判断"这个模式之前真的坏过吗"。**审查模型用便宜的/快速的，不一定要和写代码的模型同等级——省费用省时间。**

4. **第一次重复性 bug 出现时立刻立规矩** — 功能第一次跑通你不知道什么规则必要。但同一个类型的错误出现第二次时，你知道它会再来——那时候立的规矩才有针对性。hook、自检、铁律，不让同类违规再入 git。

5. **你管的不是代码，是信息流** — 数据从用户→LLM→工具→LLM→用户的链上每一个断点。用三问定位法找断点，不需要打开代码文件。

6. **同一功能区域反复出问题 → 不是缺补丁，是架构错了** — AI 永远不会主动说"这个模块该重建"。AI 只会无限打补丁。你是唯一知道"这里修过几次"的人。感觉"怎么又修这里"→ 喊停，要求 AI 重建架构。不需要数具体次数，只需要识别重复模式。

## 核心认知：你的角色

- **跨会话记忆**：AI 在单次对话内能记住上下文，但跨对话记忆为空白。每次新对话，bug 对 AI 都是"第一次见"。唯一拥有 53 天累积记忆的是你。
- **AI 没有"系统健康"概念**：你让它修 bug，它就修 bug。它不会说"修之前我们应该想想为什么这个模块反复出问题"——因为模块健康度不在它的优化目标里。它不是"速成"，是**没有全局视角**。
- **修复是做减法，不是做加法**（AI 代码中尤其成立）：AI 的倾向是加判断来消除症状，而非删冗余来修复根因。真正的修复产出的是更少的代码——拆墙，不补洞。HaGoKu 6/24 实证：两个补丁 +20 行（都撤回了），真正的修复 -135 行净删除。
- **硬编码常量是隐藏的补丁**：`MAX_TOOL_ROUNDS = 5` 看起来像"配置"，实际是代码替 LLM 决定它需要几轮。所有硬编码的阈值、上限、超时，本质上都是代码在猜 LLM 需要什么——猜错了就是 bug，且症状（字段表不显示）和根因（轮次上限）之间距离极远，极难定位。
- **拆一个墙，会看到隔壁也是墙**：修 `MAX_TOOL_ROUNDS` 的根因后，暴露了 `route_to` 是从不执行的死工具（之前轮次不够，永远走不到它），暴露了"当前关注点注入"是多余干预（之前 LLM 被掐断后行为不稳才需要它）。一次真正的根因修复会触发连锁死代码清理。
- **旧架构的残留不只是废代码，它会主动干扰新架构**（HaGoKu 证据：`replyPending` 残留状态直接导致系统卡死）。
- **操作法**：让 AI 维护一个 `CHANGES.md`，每次修 bug 记一行：日期、功能模块、问题简述。同一功能模块频繁出现 → 标记 🔴 → 你喊停，要求 AI 重建该模块。不需要懂代码，只需要识别频率和模式。

## 给自己未来项目

### 复用
- dump 从第一天（让 AI 配，你只管 `cat`）
- pre-commit hook 从第一周（或第一次重复 bug 出现后立刻）
- 工具三问：LLM 自己能做吗？描述有"何时用"吗？同一件事几个入口？
- 通道十律做项目宪章
- AI 审查 AI 做标准流程（审查用便宜模型）
- 从能跑通的最简架构开始，不预先设计复杂度。对多数项目这意味着单 Agent，但别当教条——如果业务天然需要拆成多个独立职责，直接多 Agent 也可能是对的。

### 避坑
- 功能加模块时同步加约束（成对前进，不单独堆功能）
- 先定义端到端场景再堆功能（3-5 个完整用户旅程就是验收标准）
- prompt 膨胀从源头掐（出现"禁止""不要"→ 查 mismatch，修通道，删禁止）
- 定期换 AI 审查（不让一个 AI 连续对话太久产生惯性偏差）
- **重复性 → 重建**：同一个功能区域反复出问题 → 不修，重建架构。AI 永远不会主动提议重建。
- **打补丁 = 对错误架构加倍下注**。HaGoKu 6/18 一天六次"撤回"——每个补丁都在上一个错误方向上继续走，直到塌了才被迫回头。
- **相信你的"怎么又修这里"直觉**。那不是错觉，是架构在发出信号。
- **真根因修复会照亮周围死代码**：修掉一个隐藏的硬编码限制 → LLM 行为路径全变 → 原来"不生效"的代码变成"多余"的代码 → 连锁清理。HaGoKu 6/24：一个 `MAX_TOOL_ROUNDS` 修复 → 删了 route_to 整套机制 + 关注点注入 → 净删 135 行。
- **警惕"加诊断日志"的本能**：AI 找不到根因时的默认反应是加日志。这看起来无害，但它让你错以为"在做事"，推迟了真正的根因定位。HaGoKu 6/24：加了诊断日志 → 十分钟后被撤回，因为找到了真正的根因（一个数字）。问 AI："在不加一行日志的前提下，这个 bug 的可能根因有哪些？"——强迫 AI 进推理模式，不进补丁模式。

## 三个边界条件（方法对，但前提要成立）

### 1. 版本控制习惯是救命稻草
HaGoKu 的 943 个小 commits 是你能在 53 天后回溯任何 bug 引入点的原因。**小 commit + 好 message = 时间机器。** 不用学 Git 复杂命令——让 AI 帮你 commit，你只需要说"提交，message 写 X"。但必须频繁提交，每次只改一件事。

### 2. 在你的业务领域里做项目
你能指挥 AI 做数据分析，不是因为你会写代码——是因为你懂数据分析。你知道"字段理解"、"效应量"、"置信区间"是什么，能判断 AI 的分析结果对不对。**跨到不懂的领域，你失去了唯一的锚——判断产出质量的能力。** 方法可以迁移，但项目方向必须在你的专业领域内。

### 3. 模型能力是天花板
同样的方法、同样的人，换成两年前的 LLM，可能走不到三分之一。铁律是 2026 年中的模型能力底座上建立的——模型越强，铁律越能生效。方法可以准备，但真正的上限在模型。**当模型能力再跃升一代，部分铁律可能不再需要——届时需要重新评估，别把铁律当永恒真理。**

## 关于"全是弯路"

回头看 53 天，感觉全是弯路。但这感知本身就是成长的证据。

**做个对比**：HaGoKu 6/24 的 bug（字段表不显示，根因是 `MAX_TOOL_ROUNDS = 5`）。如果这个 bug 发生在第 5 天——AI 会加至少 5 个补丁，commit 20 次，代码涨 200 行，两周后全部塌掉重来。实际上这个 bug 发生在第 53 天——两小时，两个补丁被识别并撤回，一个真正的修复（改一个数字），连锁清理 135 行死代码。

**同一个 bug，同样的你，同样的 AI。产出完全不同。** 唯一的变量是你大脑里长出来的识别回路——看到"加诊断日志"就知道是逃避，看到 15 行新增就知道太多了，看到硬编码常量就知道这是隐藏的补丁。

这些识别回路，不看 943 个 commits 长不出来。**学走路不是弯路——跌倒就是学走路的机制本身。你现在回头看觉得自己在绕弯，是因为你的眼睛比当时亮。弯路的感知是成长的副作用。**
