# 真实失效场景案例库

> **目的**：为每一次「现行犯」级真实通道失效记档。mock 测试不能脱离真实场景——本目录是**真实失效的活体样本**，每一份对应一份回归测试守护它不再发生。
>
> **使用规则**：
> - 新增 LLM 主导设计前先扫一遍——避免重复踩坑
> - 修复任何「真实失效」必须在本目录新增一份案例 + 一条回归测试
> - 案例文件不可删除（只可标记为「已根治 / 已废弃」）

## 案例模板

新建案例时复制下面骨架到 `YYYY-MM-DD-<slug>.md`：

```markdown
# 案例：<标题>

- **日期**：YYYY-MM-DD
- **状态**：🔴 现行犯 / 🟡 部分修复 / ✅ 已根治
- **报告人**：用户 / 测试 / 监控
- **相关律**：律 X / 律 Y

## 用户原话

> "..."

完整复制用户的反馈，不做总结。律 2「原话不可销毁律」也适用于本目录。

## 现象

具体看到什么？UI 上显示什么？日志里有什么？用户感受如何？

## 复现步骤

1. ...
2. ...

## 根因诊断

为什么会发生？指向具体的律违反 / 通道残缺。

## 修复

- 修了哪些文件？
- 关键 commit / PR
- 守护测试位置（断言什么）

## 影响范围

- 哪些用户已经遇到？
- 哪些用户可能也在遇到（潜在）
- 需要前端 / 后端 / 文档协同的部分

## 教训

下次设计相似 LLM 工具/暂停点时要避免什么？
```

## 何时建案例

- 用户原话级反馈：「我说了系统没反应」「分析结果错了」「我刚才说的没用」
- mock 测试全绿但用户依然遇到通道断裂
- 真实 LLM 验证抓到的失败
- 任何「下次相同设计还会再犯」的失误

## 何时**不**建案例

- 单次 prompt 调优（属于 LLM 调优范畴）
- 实现 bug（如代码笔误、import 错误）— 这些写 commit message 即可
- 性能问题（不属于通道完备性范畴）
