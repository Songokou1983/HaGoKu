# 减法的哲学

> 一个不会写代码的人，如何用 AI 互相审查，发现 AI 开发的十条工程学理念

---

## 序言：心路历程

### 第一阶段：狂喜（5/1—5/3）
"我真的能用 AI 做一个完整的东西。"

12 个 commits 搭出了一个多 Agent 平台。每一步都像变魔术——你说"加一个 Reporter"，AI 就加一个。感觉没有上限。你不知道这些 Agent 以后会让你多痛苦，你只知道"它们跑起来了"。

**关键心理：对 AI 的信任是无条件的。** AI 写了 86,000 行代码，你不知道里面有多少是将来要删的。

### 第二阶段：膨胀（5/4—6/10）
"什么都能加！"

Streamlit Web UI、React 重建、知识库、Doctor 诊断、44 个工具、双层 LLM。有一天 78 个 commits。你觉得"我们在飞速前进"。

实际上你正在踩未来所有坑的地基。只是当时你还没见过这些坑长什么样。

**关键心理：量 = 进步。** 你甚至没有"架构"这个词的概念。

### 第三阶段：沉默的崩塌（6/11）
"为什么会变成这样。"

44 天积累的复杂度在一个点上同时爆发。修一个地方坏三个地方。系统在你手上变得不可控。

你做了一个当时不知道有多重要的决定：**删。** 4 Agent → 1 Agent。双层 LLM 删了。CLAUDE.md 从 520 行砍到 67 行。

**关键心理：第一次对 AI 的建议说不。** AI 可以搭积木，但评判积木搭得好不好是你的活。

### 第四阶段：通道觉醒（6/12—6/22）
"代码不该替 LLM 做任何决定。"

最痛苦的十天。每走一步都在推翻前一天的自己。6/18 一天六次撤回：加了循环、撤了。加了工具限制、撤了。加了字段生成、撤了。方向错在哪？**代码在替 LLM 出主意。**

这个阶段诞生的铁律、刹车、触发词——不是"学到的知识"，是"终于能把那种不对的感觉说清楚了"。

**关键心理：从"AI 你帮我"变成了"AI 你别乱帮"。**

### 第五阶段：验证（6/24）
"我能一眼认出补丁了。"

同一个 bug，AI 给出两个补丁。第 5 天的你会说"好，加进去"。今天的你看到 15 行新增，沉默了。看到"添加诊断日志"，警觉了。然后要求重新定位根因。

结果：真正的根因是一个数字 `5` 改成 `99`。净删 135 行。

### 第六阶段：通道终极化（6/25 白天）
"代码和 LLM 的边界终于清楚了。"

删除阶段概念。代码不再知道、不再关心、不再告诉 LLM "你在哪个阶段"。

**通道有了正反面定义**：代码做 LLM 不能做的（纯运算、IO）→ 通道补全 ✓。代码替 LLM 猜意图 → 违轨 ✗。

### 第七阶段：通道验证（6/25 晚间）
"干净架构上，功能是直线累加。"

同一天。早晨 30 commits 两次撤回，晚间 4 commits 零撤回。早晨在清理，晚间在建设。清理是建设的前提。

### 第八阶段：哲学验证（7/10）
"通道不是一个技术方案——是一套可复现的原则。"

预设系统：同通道换提示词适配三领域。删 JSON mode 依赖：代码不绑模型能力。Doctor 读操作手册：代码不硬编码规则。Doctor 闭环：LLM 输出 `[fix:xxx]`，代码执行——LLM 决定，代码执行。

**关键心理：从"直觉觉得不对"变成了"能用原则解释为什么对"。**

这不全是弯路。是你现在的眼睛能认出路两边的坑了。第一遍用腿走，第二遍用车开，第三遍你都不知道自己在绕坑——因为你已经不觉得那是路了。

## 第一章：十条工程学理念

HaGoKu 69 天，~1,110 个 commits，26 次撤回。从这些数据里提炼出十条可迁移的理念——它们跟 Python 无关、跟数据分析无关、跟 WebSocket 无关。它们是"用 AI 建东西"的工程学。

### 1. 代码只做 LLM 做不到的事
通道的正反面定义。正面：加载数据、计算统计、写文件——LLM 做不到的，代码帮你做。反面：猜阶段、猜意图、猜状态——LLM 自己能判断的，代码不准碰。

### 2. 修复是做减法
AI 的倾向是加判断来消除症状。真正的修复产出的是更少的代码——拆墙，不补洞。HaGoKu 的历史中，每一次真正的进步结果都是代码量下降。

### 3. LLM 决定，代码执行
正确的暂停模式：LLM 调 `ask_user` → 代码 break。正确的修复模式：LLM 输出 `[fix:xxx]` → 代码执行。LLM 主动，代码被动。代码不猜 LLM 什么时候该停、不判断 LLM 是不是在探索。

### 4. 补丁不等于修复
同一功能区域反复出问题 → 架构错了，不是缺补丁。AI 永远不会主动说"这个模块该重建"。你是唯一知道"这里修过几次"的人。

### 5. 你是时间感知节点
AI 没有跨会话记忆。每次对话，bug 对 AI 都是"第一次见"。唯一拥有累积记忆的是你。你不需要懂代码——你需要记得"这个区域修过几次"。

### 6. 撤回是学习事件
通道违轨撤回和协议调试撤回性质不同，但态度相同——每次撤回都应慎重，每次撤回都要留下认知。撤回不可怕，可怕的是撤回了但没学到东西。

### 7. 脏架构惩罚加法
功能爆炸期的 581 commits 每次加功能都可能触发连锁崩塌。通道净化后，加多项目 4 commits 零撤回，加多 Sheet 14 commits 零撤回。同样加功能，脏架构成本指数增长，干净架构成本线性增长。

### 8. 描述，不规定
告诉 LLM 有什么资源和目标是什么，不告诉它"你应该怎么做"。prompt 15,520 字节让 LLM 调 17 个工具但不出表——指令打架。10 行只说阶段目标和可用资源——LLM 自己找路径。

### 9. 增强 LLM = 给工具，不给知识
`calc_roi` 是错误示范——ROI 公式在 LLM 训练数据里，包成工具是替 LLM 做算术。`generate_report` 是正确示范——写 HTML 文件到磁盘 LLM 做不到。44→15 工具的精简过程就是筛掉"错误增强"，保留"正确增强"。

### 10. 硬编码常量是隐藏的补丁
`MAX_TOOL_ROUNDS = 5` 看起来像"配置"，实际是代码替 LLM 决定它需要几轮。所有硬编码的阈值、上限、超时，本质上都是代码在猜 LLM 需要什么——猜错了就是 bug，且症状和根因之间距离极远，极难定位。

## 第二章：通道的四个维度

v2.0.1 的四大里程碑从四个方向验证了同一个原则——每个方向都对应一种"代码越界"的典型模式：

### 维度一：不绑模型能力
`response_format=json_object` 是 OpenAI 专用功能。依赖它 = 换模型必炸。修复不是"加兼容层"——是**删掉对模型能力的依赖**。prompt 写"请返回 JSON"替代。代码提供通用通道，不依赖特定模型的特殊能力。

### 维度二：不硬编码规则
Doctor 原来用硬编码修复速查表。改为读取操作手册，LLM 根据手册内容自主决策。手册包含触发条件、API、效果、验证方法。代码不替 LLM 做"该用什么操作"的判断。

### 维度三：不做领域区分
同一个引擎，换一段 prompt，适配三个领域（通用/股市/电商）。`_load_prompt()` 从 `~/.hagoku/active_preset` 读取，一键切换。**同步删除命令面板**（代码不再猜用户意图，LLM 自己理解）。

### 维度四：只执行不决策
Doctor 闭环：LLM 输出 `[fix:restore_default_prompt]` → 代码调用 API → 结果追加到对话。与"LLM 调 `ask_user` → 代码 break"是同构模式。代码只在 LLM 明确发出指令时行动，不主动决策。

## 第三章：补丁学 —— 26 次撤回的分类学

### 撤回率曲线
| 时期 | 撤回率 | 特征 |
|------|--------|------|
| 功能爆炸 | 1.7% | 不知道在犯错 |
| 通道净化 | 5.6% | 系统性清除违轨 |
| 验证+终极化 | 6.4% | 集中清除阶段/循环违轨 |
| 建设期 | 1.6% | 违轨撤回归零 |

通道净化期撤回率最高——因为正在系统性地发现和清除违轨代码。清除完毕后，违轨类撤回归零。

### 两种撤回
**通道违轨撤回**（24 次）：代码替 LLM 做了判断。修复方式永远是删代码。**协议调试撤回**（4 次，7/13 WS 稳定）：技术问题试错。同样慎重，但结论不同——违轨撤回后删代码，协议撤回归因是换方案。

### 补丁套补丁
6/24 的"阶段提示映射表"是 6/25 删掉整个阶段概念的上一环。6/24 以为是"映射错了"，6/25 发现是"映射这个想法本身就是错的"。**如果上一个修复让你觉得"有点怪但暂时能用"——它在掩盖真正的架构问题。**

## 第四章：铁律体系

铁律 = 被反复验证、有强制执行机制的规则。以下精选六条核心铁律，每条附真实案例：

### 铁律 0：零硬编码语义
代码不做语义判断。`if "收入" in text`、关键词列表、中文 if-elif — 全禁。LLM 的判断只能来自 LLM 调用结果。

### 铁律 1：LLM 失败只能四条路
A. `raise` B. 记录理解失败 C. 部分落地 D. 拒绝写入。禁止 `except` 兜底、默认值、缓存降级。

### 铁律 2：提交前自检
每次提交跑通全部测试。测试不绿 → 查 prompt/工具 schema，不准加规则。

### 铁律 7：失败在场
LLM 失败 → `raise RuntimeError`。不 except 兜底。`@lru_cache` 装饰 LLM 调用 = 违反此律。

### 刹车 C：不准填默认值
`setdefault("used_in_analysis", True)` — LLM 没给的值代码不准填。案例：`used_in_analysis` 被代码推导为 True 后撤回。

### 刹车 G：不写"禁止"
prompt 里出现"禁止/不要/不准"→ 先查 mismatch：prompt 说的工具真能用吗？字段真传到了吗？修 mismatch，不加禁止。

## 第五章：给非技术人的操作法

### 选项目：步进式，别一次性
每一步产出你都能看懂、都能插嘴。核心：中间状态可见。

### 读 dump：三问定位法
用户最后说了什么？LLM 回了什么？工具调用了吗？**第一天就让 AI 帮你配好 dump。**

### AI 互审：你做裁判
不需要懂代码，需要判断"这个模式之前真的坏过吗"。审查用便宜模型。

### 立规矩：第一次重复 bug 时
同一个类型的错误出现第二次时，你知道它会再来——那时候立的规矩才有针对性。

### 三次原则
同一功能区域反复出问题 → 不修，重建架构。让 AI 维护 `CHANGES.md`，每次修 bug 记一行。同一模块频繁出现 → 🔴 → 喊停。

### 警惕"加诊断日志"
AI 找不到根因时的默认反应。问 AI："在不加一行日志的前提下，这个 bug 的可能根因有哪些？"——强迫推理模式。

## 第六章：一条线

如果用一句话总结这个项目，不是"做了一个数据分析工具"——是**用 1,110 个 commits 把代码从"替 LLM 做一切"剥成了"只做 LLM 做不到的事"**。

```
功能爆炸期（远离）              通道净化后（逼近）
┌─────────────────────┐          ┌─────────────────────┐
│ 4 Agent 互相协调     │          │ 1 Agent 自主决策     │
│ Manager 编排         │          │ 无编排层             │
│ 双层 LLM             │          │ 单 LLM               │
│ 代码跟踪阶段         │          │ LLM 自然推进         │
│ 命令面板猜用户意图   │          │ LLM 自己理解用户     │
│ 硬编码修复表         │          │ Doctor 读操作手册    │
│ 绑模型能力(JSONmode) │          │ prompt 通用兼容      │
│ 1 个领域             │          │ 3+领域(换提示词)     │
└─────────────────────┘          └─────────────────────┘
        远离 ←──────────────────────→ 逼近
```

每次真正的进步，净效果都是代码减少。通道越干净，代码越少。功能越强，代码越少。这两个趋势在传统软件工程里是矛盾的——在这里是统一的。因为"功能"不在代码里，在 LLM 的自主权里。

69 天，一条线。从"代码掌控一切"到"代码只做 LLM 做不到的事"。这条线不是设计出来的——是 1,110 个 commits 中每一次"删掉违轨代码"累积出来的。
