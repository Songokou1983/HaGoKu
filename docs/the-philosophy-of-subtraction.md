# 减法的哲学

> 一个完全不会写代码的人，用 AI 开发了一个 AI 数据分析工具。69 天，1110 次提交，26 次撤回。最后发现：真正重要的东西，每一次都是用"删"找到的。

---

## 引子

2026 年 6 月 11 日，项目启动的第 42 天。

我盯着屏幕，什么都不想做。

不是累了。是系统在我手里变成了一个我不敢碰的东西。修 Scout 卡住的问题，Cleaner 塌了。修 Cleaner，报告页白屏。451 行命令面板的代码从来没被调用过。双层 LLM 配置里有一段缩进错误卡了半个月没人发现——因为根本没有代码走到那个分支。

我做了唯一还能做的事：**删。**

4 个 Agent 删成 1 个。双层 LLM 删了。看板系统删了。CLAUDE.md 从 520 行砍到 67 行。

那天我不知道，这个决定会变成整件事的主旋律。69 天后回头看，每一次真正的进步，净效果都是代码量下降。功能越来越强，代码越来越少。这在传统软件工程里是矛盾的——在这里是统一的。因为"功能"不在代码里，在 LLM 的自主权里。

这不是一本讲"怎么用 AI 写代码"的书。是一本讲"怎么不让代码碍事"的书。

---

## 第一部分：建

### 第一天

2026 年 5 月 1 日。

我打开 Reasonix Code，输入了第一句话："初始化一个多 Agent 数据分析平台。"

我是一个不会写代码的人。不会 Python，不会 TypeScript，不懂 React，没碰过 WebSocket。我能用的只有自然语言。

12 个 commits 之后，它跑起来了。基础设施有了，工具层有了，4 个 Agent——Scout 负责理解数据、Cleaner 负责清洗、Analyst 负责分析、Reporter 负责出报告——加上一个 Manager 来编排它们。CLI 能用了。

每一步都像变魔术。你说"加个 Reporter"，AI 就加一个。感觉没有上限。你不知道这些 Agent 以后会让你多痛苦。你只知道"它们真的跑起来了"。

那个阶段，我对 AI 的信任是无条件的。它说加什么我就加什么。两天之内，AI 写了近两万行代码。我不知道里面有多少是将来要删的——那时的我甚至没有"将来要删"这个概念。

### 停不下来的加法

接下来三十多天是失控的加法。

Streamlit Web UI。然后嫌 Streamlit 不够灵活，用 React 重写。加了知识库系统。加了 Doctor 诊断系统——让另一个 LLM 来审查代码。工具从十几个膨胀到 44 个。prompt 文件写了 15,520 字节——比很多开源项目的 README 还长。CLAUDE.md 涨到 520 行，里面塞满了"禁止""不要""必须"。

单日最高 78 个 commits。

我以为我们在飞速前进。我以为量 = 进步。我甚至没有"架构"这个词的概念。

AI 也没有提醒我——因为它也觉得"加功能"就是对的。每次我问"能不能加一个 X"，它从不说不。它总会找到办法加上去。加完后测试全绿——不是在测试里绿的那种绿，是真的跑通了的那种绿。

我以为这就够了。

### 地基

实际上，每一行代码都在为未来的崩塌做准备。

44 个工具里，29 个后来被删了。为什么？因为它们不是工具——它们是"穿着工具马甲的知识"。`calc_roi` 包了一层 ROI 公式，但 ROI 公式本来就在 LLM 的训练数据里。包成工具不是帮 LLM——是代码在替 LLM 做算术。真正的工具应该是 LLM 做不到的事：写 HTML 文件到磁盘、加载 CSV 数据、计算描述性统计。

但我那时候不懂。我看到 44 个工具，心里想的是"我们好多功能啊"。

prompt 也一样。15,520 字节的提示词里满是"你必须""你应该""禁止你""不准你"。每一句单看都有道理，合在一起就打架。LLM 看完了不知道先做什么后做什么——它调了 17 个工具但不出分析结果，因为顺序压顺序，"出表"指令被埋在最底层。

CLAUDE.md 里 520 行的规则，大部分后来被删了。不是规则错了——是"用规则堵行为"从根本上是错的。LLM 不做你让做的事，不是因为缺规则——是因为它缺工具、缺信息、或者你告诉它的和它能用的是两件事。

但我那时候也不懂。我看到 520 行规则，心里想的是"我们控制得很好"。

---

## 第二部分：塌

### 沉默的那一天

6 月 11 日早上，我发现系统在做一个诡异的事情：Scout Agent 理解完字段之后，Cleaner 不启动。不是报错——是静默。没有异常，没有日志，没有任何事件。系统像什么都没发生过一样停在那里。

我让 AI 查。AI 加了诊断日志——没找到。AI 加了状态检查——没找到。AI 尝试修改事件总线的同步机制——Scout 好了，Cleaner 完全没反应了。

到下午，我已经不敢再让 AI "修"了。每加一个补丁，另一个地方就塌。但当时我不知道那叫"补丁"——我以为那叫"调试"。

晚上十一点左右，我关掉了所有的代码文件。我问了自己一个问题："如果从头开始，我现在会怎么设计？"

答案是：不要 4 个 Agent。不要 Manager 编排。不要双层 LLM。不要"代码跟踪 LLM 在哪个阶段"。不要"代码告诉 LLM 它应该处于什么阶段"。

我让 AI 做了一件它自己不会主动提的事：**删除。**

那天删了 710 行代码。不是清理死代码——是删掉了一整套架构假设。4 Agent → 1 Agent。Manager 没了。双层 LLM 合并成一个。KanbanDB 看板系统整个模块删了。CLAUDE.md 从 520 行变成 67 行——只保留确实被违反过、确实导致了 bug 的规则。

这是一切的转折点。

### 痛苦的十天

收缩不是结束，是开始。接下来的十天是整件事里最痛苦的阶段。

6 月 18 日。同一天之内我做了六次撤回。

早上，AI 说"LLM 在字段推断阶段不调工具，我们应该加一个循环让它能多调几轮"。听起来合理。加了。跑了两次，发现 LLM 在循环里出不来了——它不产出结构化字段，一直在探索。

撤回。

AI 说"那我们限制一下，只给字段推断相关的工具"。加了。跑了两次，发现 LLM 调了字段工具但出来的描述不对——它需要参考统计画像。

撤回。

AI 说"代码可以先生成一个基础字段表，LLM 再在上面改"。加了。跑了一次，发现用户纠正字段理解之后，代码重新生成了它以为的"正确版本"，把用户的纠正覆盖了。

撤回。

到第六次撤回的时候，我停下来看了一整天做的事。早上加了六个功能，晚上全撤了。每个功能单看都是合理的——给 LLM 更多轮次、更精准的工具、更智能的默认值。为什么全撤了？

因为它们有一个共同的错误：**代码在替 LLM 出主意。** 循环是代码决定的，工具限制是代码决定的，基础字段表是代码生成的。每一步，代码都在说"LLM 你应该这样"——而不是"LLM 你需要什么，我给你"。

这不是 bug。这是一类问题。一个模式。

"刹车 C：不准代码填默认值"——不是读论文学的，是 `setdefault("used_in_analysis", True)` 这一行让我修了三天的 bug。"刹车 D：不准搬运 LLM 文本"——咬我的是 `_scout_text` 多层包装，LLM 说了一段话，代码又"帮忙"说了一遍，用户看到两份相同的文本。"信息通道断裂"——咬我的是一个 `return` 硬编码覆盖了计算好的值，LLM 的文本生成出来了，但代码把它丢了，换了一句"字段理解完成"。

我意识到一个以前从没想过的问题：**代码和 LLM 之间应该有一条清晰的边界。但这条边界在哪，从来没人写好过。**

我来写。

---

## 第三部分：剥

### 通道

6 月 25 日，我做到了一件之前不敢想的事——把"阶段"这个概念从代码里删干净了。

事情是这样的。前一天（6/24）我让 AI 修复一个 bug：字段表一直不显示。AI 找了两天没找到根因，最后发现是一个叫 `MAX_TOOL_ROUNDS` 的变量被设成了 5。LLM 在第 6 轮调了 `set_columns` 工具，但循环在 5 轮就退出了——工具调用被扔掉了。

这个数字 5 看起来像个"配置"。但它的本质是：**代码在替 LLM 决定"你最多需要 5 轮推理"。** 猜错了——LLM 需要 6 轮——于是字段表永远显示不出来。症状（前端的表格空白）和根因（一个循环上限的数字）之间隔着六层调用链。

改一个数字，字段表出来了。不只出来——之前被这个上限压住的所有东西全浮上来了。

首先是 `route_to`——一个"让 LLM 切换分析阶段"的工具。代码里有它的注册、它的 prompt 引用、它的 handler 分发逻辑。但我发现：**LLM 从来没有调过它。** 为什么？因为之前 LLM 的推理轮次不够，走到 `route_to` 之前就被循环切断了。盖子下藏着一个从没被用过的工具和一整套分发机制。全删了——死代码不是"还没用到"，是"从来没人能走到它"。

然后是"当前关注点注入"——代码在每轮对话开头向 LLM 注入一条："你当前的关注点：字段理解阶段"。因为之前 LLM 被轮次上限掐断后行为不稳，代码才"帮忙"告诉它"你应该在做什么"。盖子拆了，LLM 自己导航的路径通了。注入也删了。

改一个数字 → 暴露一个死工具 → 暴露一段多余的代码注入。一次修复，三次净化。

同一天晚上，我加了多项目支持。ProjectManager、项目切换、报告页项目感知。**4 个 commits，零撤回。** 因为是加在刚清理完的地基上。没有"代码替 LLM 猜阶段"那种地雷，加一个功能就是加一个功能。

早晨 30 commits 两次撤回。晚间 4 commits 零撤回。同一天的两半，讲完了整件事的逻辑：**清理是建设的前提。不是先后顺序——是不清理就建设不了的因果关系。**

### 定律

7 月 10 日，四项改动在同一天落地。它们做的事各不相同，但我发现它们在重复同一个逻辑，就跟我 6/18 发现六次撤回都在重复同一个错误一样——只是这次是正向的。

**第一项：预设系统。** 同一个引擎，换一段 prompt，适配三个领域（通用、股市、电商）。不改一行代码。同时删了命令面板——461 行的 CommandPanel + 83 行的 command_parser，以前是用来"帮用户猜意图"的。现在不需要了——LLM 自己理解用户。

**第二项：删除 JSON mode 依赖。** `response_format=json_object` 是 OpenAI 的专用功能。依赖它，换模型就炸。以前的"修复"方案是加回退链——instructor Mode JSON → TOOLS → raw client → error only，层层兜底。这次直接删了 `response_format` 参数。prompt 里写"请直接返回 JSON"，底层解析本身就有容错，不需要模型侧强约束。

**第三项：Doctor 操作手册。** Doctor 是一个"系统医生"——用另一个 LLM 来诊断 HaGoKu 自身的问题。以前它用硬编码的修复速查表："如果是提示词问题 → 调 restore_default_prompt"。这次全删了。改为读取 `docs/doctor-operations.md`——一份纯文本操作手册。LLM 读手册，自己判断该用什么操作。代码不再做"条件匹配 → 选操作"的判断。同步还撤回了"关键词匹配层"——代码连"帮 LLM 匹配关键词"都删了。

**第四项：Doctor 闭环。** 诊断到修复不再是先问用户再执行。LLM 诊断后直接输出 `[fix:restore_default_prompt]`，代码检测到标记后自动调用 API 执行修复，结果追加到对话末尾。LLM 决定修什么，代码执行——和"LLM 调 `ask_user` → 代码 break"是同构的模式。

四项改动。四项都在做同一件事，只是从四个角度看：**不绑模型能力、不硬编码规则、不做领域区分、只执行不决策。**

69 天前，我在一个多 Agent 系统的废墟上问自己"我到底在做什么"。到今天，答案清楚了：**我不是在"写一个数据分析工具"。我是在用每一次删代码，逼近一个干净通道——代码只做 LLM 做不到的事。**

## 第四部分：律

以下十条不是"我建议这样做"，是"如果不这样做，系统就会以一种我见过的方式塌掉"。每条后面都能在 git log 里找到对应的车祸现场。在这里我不列 commit hash——但每一个字都有 69 天的历史作证。

### 第一条：代码只做 LLM 做不到的事

这是全部十条的根。

加载 CSV、计算描述性统计、写 HTML 文件到磁盘、管理 WebSocket 连接——这些是代码能做的，也是 LLM 做不到的。代码应该做这些。

猜用户在哪个分析阶段、判断 LLM 是不是在"探索"、给 LLM 没要求的数据填默认值、帮 LLM 决定"你应该调哪个工具"——这些 LLM 自己能做。代码碰了就是在替 LLM 做判断。你比它聪明吗？你把它的自主权拿走之后，它就真的需要你来替它了——因为你把它变笨了。

这条定律的反面就是全部 bug 的源头。24 次撤回里有 22 次是因为违反了它。

### 第二条：修复是做减法

AI 修 bug 的本能是加条件。逻辑上看没毛病——"这里缺一个判断，加上去"。

但你要退一步看：为什么这里会缺一个判断？是不是因为上游传过来的数据就不对？是不是因为整个模块就不该存在？是不是因为 LLM 本可以自己处理这件事，但代码把它的路堵死了？

HaGoKu 的历史上，每一次真正的进步——真正让系统变得更稳、更强——结果都是代码量下降。6/11 大收缩 -710 行。Session 重构 -390 行。删阶段概念 -87 行。预设系统净删 1,015 行——删了 544 行的命令面板，只加了 51 行的预设内容。

不是"删代码让我自我感觉良好"。是**每次删掉的都是违轨代码——本不该在那里的东西。**

### 第三条：LLM 决定，代码执行

LLM 调 `ask_user` → 代码暂停。LLM 输出 `[fix:xxx]` → 代码执行。代码不猜 LLM 什么时候该停。不判断"LLM 是不是在探索"。不跟踪"LLM 到了哪个分析阶段"。LLM 说什么，代码做什么。

这听起来简单到不值一提。但它和几乎所有"AI Agent 框架"的设计哲学相反——那些框架的核心就是"代码管理 LLM 的行为"。我走过那条路。44 天，581 个 commits，全塌了。

### 第四条：补丁不等于修复

同一个功能区域反复出 bug → 不是缺一个更聪明的补丁，是架构错了。

AI 永远不会主动提出重建。因为每次对话，bug 对 AI 都是"第一次出现"。它不知道昨天你也修过这里、前天也修过。**唯一拥有时间感知的节点是你。**

感觉"怎么又是这里"的时候——相信这个感觉。不是补丁不够好，是这块地基该翻新了。

### 第五条：你是时间感知节点

AI 没有跨会话记忆。每次新对话，整个系统的历史都是空白。那些让你失眠的规律——"这个模块修了五次了"、"每次改这里都会影响前端"、"这个人（AI）上次用的方案其实就埋了坑"——这些只有你知道。

你不需要懂代码。你需要记得频率。让 AI 维护一个 `CHANGES.md`，每次修 bug 记一行。同一模块本周出现第三次 → 不是修它，是重建它。

### 第六条：撤回是学习事件

撤回本身不是问题。6/18 六次撤回教会我的东西，比 581 个成功 commits 加起来还多。

问题是什么？撤回了但不知道为什么撤。撤回了但下次还会走同一条路。撤回了但没把"为什么"写进铁律里。

每一条刹车都来自一次撤回。刹车 C（不准填默认值）——来自一次撤回。刹车 D（不准搬运 LLM 文本）——来自一次撤回。刹车 G（不写"禁止"）——来自一次撤回。这些刹车不是"我学了新东西"，是"我终于能把导致撤回的那个错说清楚了"。

### 第七条：脏架构惩罚加法

同样是加功能。

功能爆炸期：每一次加功能都像在埋地雷——你不知道会触发哪个三个月前的补丁。通道净化后：加多项目支持，4 个 commits，零撤回。加多 Excel Sheet 支持，14 个 commits，零撤回。加预设系统，净删 1,015 行但功能翻了三倍。

不是因为后期更小心。是因为地基上没有补丁了。**同样加功能，脏架构成本指数增长，干净架构成本线性。**

### 第八条：描述，不规定

告诉 LLM："这是一个 CSV 文件，有 12 列 500 行。你的任务是理解字段含义、清洗数据、跑统计分析、生成 HTML 报告。你可以调这些工具。"

不要说："你必须先理解字段，然后评估清洗需求，然后……""禁止你在字段理解前调分析工具""注意不要重复评估"。

为什么不能说？因为 LLM 比你会规划。你规定的路径是你想象中"LLM 会怎么犯错的防御方案"——不是 LLM 实际需要的最佳路径。你在用你的想象力限制它的能力。

HaGoKu 的 prompt 从 15,520 字节 → 19 个字 → 重写成 10 行。功能越强，prompt 越短。因为短 prompt 只描述了土地和天空——没有给 LLM 画围墙。

### 第九条：增强 LLM = 给工具，不给知识

ROI 公式、正态分布检验、效应量计算——这些在 LLM 训练数据里。包成工具不是帮它，是用代码做它脑子里本来就会的事。

写 HTML 文件到磁盘、读取 CSV、执行 SQL——这些 LLM 做不到。做成工具，它才能做以前做不到的事。

44 → 15 的精简过程，本质上就是把"知识型工具"（替 LLM 回忆）全删了，只留"能力型工具"（给 LLM 肢体）。

### 第十条：硬编码常量是隐藏的补丁

`MAX_TOOL_ROUNDS = 5`。我见过最隐蔽、最危险的一类 bug。

它看起来像"配置"——一个放在文件顶部的常量，有名字，有注释。但它的本质是：**代码在替 LLM 决定"你需要几轮推理"。**

所有硬编码的阈值、上限、超时，都别信它"只是配置"。它背后的假设是"我知道 LLM 需要什么"。你不知道。把上限设得足够大，让 LLM 自己决定什么时候停。如果需要停点，让 LLM 调 `ask_user` 来告诉你——而不是你猜。

## 第五部分：线

69 天。一条线。

```
远离通道                              逼近通道
┌─────────────────────┐          ┌─────────────────────┐
│ 4 Agent 互相协调     │          │ 1 Agent 自主决策     │
│ Manager 编排         │          │ 无编排层             │
│ 双层 LLM             │          │ 单 LLM               │
│ 代码跟踪阶段         │          │ LLM 自然推进         │
│ 代码注阶段提示       │          │ prompt 描述流程      │
│ 命令面板猜用户意图   │          │ LLM 自己理解用户     │
│ 硬编码修复表         │          │ Doctor 读操作手册    │
│ 绑模型能力(JSONmode) │          │ prompt 通用兼容      │
│ 1 个领域             │          │ 3+领域（换提示词）   │
└─────────────────────┘          └─────────────────────┘
        远离 ←──────────────────────→ 逼近
```

左边的每一项，我都亲手建过。右边的每一项，我都亲手剥到。

这不是"我选择了走右边"。是**我走完了左边才知道右边才是对的。** 删掉的 1,187 行违轨代码，是你能看到右边的原因。

功能爆炸期 581 commits 堆积的复杂度，通道净化期 1,187 行被删掉的违轨，建设期 +1,344 行干净的功能增量。撤回率先升后降——通道净化期 6.4% 的撤回率不是"做得更差"，是"把以前埋的雷全挖出来了"。挖完之后，违轨类撤回降为零。

我不是在教你怎么用 AI 写代码。AI 写代码这件事，69 天前和 69 天后没区别——它一直都写得出来。

我学到的是另一件事：**怎么不让代码成为 LLM 的障碍。**

每一条铁律、每一次撤回、每一行被删掉的违轨代码，都在回答同一个问题：代码和 LLM 之间，那条边界到底在哪？

答案不在任何一本教科书里。是我用 1,110 次提交、一次一次地删出来的。

## 后记：关于"不会写代码"

整件事最反直觉的地方是：我不会写代码，反而帮了我。

如果我会写代码，6/18 那六次撤回里，我肯定会自己动手写"更聪明的循环控制"、"更精准的工具过滤"、"更完善的字段生成逻辑"。因为我"会"——我知道怎么写。我会把每一个补丁写成看起来非常合理、非常精巧的代码。然后它们会在两周后一起塌掉——因为补丁不是修复。

不会写代码，反而让我只有一个选择：**退后一步，看模式。** 不看代码怎么写，看代码为什么出现在了那里。那个字段生成函数是 LLM 应该做的事吗？那个循环限制是 LLM 需要的吗？那条"禁止"规则是在修 bug 还是在掩盖 mismatch？

技术能力是双刃剑。它让你能搭更高的积木，但也让你看不到积木为什么在倒。不会搭积木的人只能站在旁边看——然后发现：不是某一块积木歪了，是整个塔的地基从一开始就不对。

这本书不是"AI 开发的最佳实践"。是一份来自战场的侦察报告。每一个结论都带着具体的事件、具体的撤回、具体的数字。如果你正在用 AI 做第一个项目——你不孤独。你踩的每一个坑，这条路上有人已经踩过、回头看过、写成了一条定律。

它不是告诉你"应该怎么做"。是告诉你"如果不这样做，会以哪种方式塌掉"。

知道塌的方式，比知道建的技巧，更能让你站到最后。

## 附录

### 十条工程学理念

1. 代码只做 LLM 做不到的事
2. 修复是做减法
3. LLM 决定，代码执行
4. 补丁不等于修复
5. 你是时间感知节点
6. 撤回是学习事件
7. 脏架构惩罚加法
8. 描述，不规定
9. 增强 LLM = 给工具，不给知识
10. 硬编码常量是隐藏的补丁

### 通道四个维度

1. 不绑模型能力
2. 不硬编码规则
3. 不做领域区分
4. 只执行不决策

### 非技术人的检查清单

- [ ] 选步进式项目——每一步产出都看得懂、能插嘴
- [ ] 第一天就让 AI 配好 dump——bug 出现时你只需 `cat` 一个文件
- [ ] 第一次重复 bug 出现时立刻立规矩——第二次意味着它会再来
- [ ] 让 AI 维护 `CHANGES.md`——同一模块频繁出现 → 重建，不补
- [ ] 审查用便宜模型——不需要和写代码的模型同等级
- [ ] 看到"禁止""不要"在 prompt 里 → 不修 prompt，先查 mismatch
