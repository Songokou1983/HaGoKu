# 数据清洗审查报告

## 一、硬编码模块确认

当前数据清洗流程存在 **三层硬编码**，决策链路上没有 LLM 参与：

### 1. 异常值检测：固定统计阈值

| 位置 | 硬编码项 | 说明 |
|------|---------|------|
| `tools/cleaning.py` `detect_outliers_iqr()` | IQR × 1.5 | 对所有数值列无条件使用相同阈值 |
| `tools/cleaning.py` | 仅检测数值列，跳过日期/文本 | 无法识别「收入」列 vs「评分 1-10」列的语义差异 |
| `tools/cleaning.py` | 仅用 IQR 方法 | 无 Z-score、MAD、百分位等替代方案供 LLM 选择 |

### 2. 清洗策略：无差别 winsorize

| 位置 | 硬编码项 | 说明 |
|------|---------|------|
| `agents/cleaner/agent.py` `_auto_clean()` | 无条件 winsorize（P1/P99） | 对所有 IQR 检测到的异常列执行相同操作 |
| `agents/cleaner/agent.py` | 无下游分析目标感知 | 不知道用户要「算均值」还是「建预测模型」还是「看分布」 |
| `agents/cleaner/agent.py` | 无字段角色感知 | 无法区分目标变量（应保守）和协变量（可温和处理） |

### 3. 管道分类：关键词 → 模板映射

| 位置 | 硬编码项 | 说明 |
|------|---------|------|
| `manager/query_parser.py` | 关键词匹配（如「趋势」「预测」「对比」） | 用户说「看收入分布」可能被错误归类，决定是否走清洗 |
| `manager/orchestrator.py` `PLAN_TEMPLATES` | 固定模板 → Agent 组合 | 只有「数据画像」跳过清洗，其他模板清洗必经 |

### 4. 对比：Scout 已有 LLM 原生模式

`agents/scout/agent.py` 中存在 `_run_in_llm_native_mode()` 方法：
- LLM 直接看数据样本
- LLM 自主判断每列的语义角色
- LLM 输出结构化 JSON，代码仅做解析和校验

**Cleaner 完全没有对标此模式**，而是用硬编码 IQR + winsorize 覆盖所有场景。

## 二、客户体验视角

以下问题从**用户感知**角度描述当前清洗模块的不足。

### 问题 1：用户不知道「为什么动我的数据」

**现状**：清洗报告输出「IQR 检测到 47 个异常值(7.6%)，Winsorize 截断优于删除」。

**客户体验**：用户不是统计学家。他们关心：
- 「Inc1 列有 47 个值超出正常业务范围，会严重拉偏平均收入，建议将超过 P99 的值截断为 P99 值」

**缺失**：每个清洗操作缺少**人类可理解的业务理由**，而是用统计术语解释。

### 问题 2：清洗策略与分析目标脱节

**现状**：无论用户想做什么分析，清洗策略完全相同（IQR → winsorize）。

| 用户想做 | 当前系统行为 | 应该的行为 |
|---------|------------|----------|
| 「看看收入分布」 | winsorize 截断极端值 | **不该截断**，极端值是用户想看的信息 |
| 「预测客户流失」 | 同上 | 极端使用量可能是流失信号，不应处理 |
| 「找高价值客户」 | 同上 | 极端值就是答案，清洗 = 毁掉结果 |
| 「A/B 测试转化率」 | 同上 | 应保守处理协变量，不碰分组列和转化标记 |

**客户体验**：用户发现自己的 VIP 客户数据被截断了，但不知道为什么。

### 问题 3：无法区分列的语义边界

**现状**：所有数值列一视同仁——IQR 检测，winsorize 截断。

**场景**：数据里有一个「满意度评分 1-5」列。系统检测到评分 1 和 5 是「异常值」（因为 IQR 窄），然后 winsorize 把 1 改成 1.5，把 5 改成 4.5。

**客户体验**：用户看到清洗后的评分数据，以为自己没有不满意的客户（没有 1 分）也没有特别满意的客户（没有 5 分）——这完全是**数据篡改**。

### 问题 4：清洗不可逆且不透明

**现状**：清洗直接修改数据，用户只能看到摘要报告，无法逐列回溯「改了哪些行的哪些值」。

**客户体验**：
- 「我的数据为什么少了 30 行？」（删行未解释）
- 「这列的值怎么全变了？」（winsorize 不可见）
- 「能不能只清洗一部分列？」（当前不支持逐列确认）

### 问题 5：缺少分析目标的前置确认

**现状**：用户上传数据后，系统自动判断分析类型（关键词匹配），用户没有机会确认。

**客户体验**：用户上传了销售数据，想知道「各地区的收入分布」。系统识别为「趋势分析」，对收入列做 winsorize，把几个大单客户数据截断了。用户看到报告后质疑：「我就是要看哪些客户贡献大，你为什么把大单改了？」

**正确流程**：用户上传数据 → 系统询问分析目标 → 用户确认 → 基于目标选择相关字段 → 基于字段角色决定清洗策略。

## 三、改进方向

### LLM 原生接管（对标 Scout 模式）

**核心原则**：LLM 做决策，代码做执行。

| 角色 | 职责 |
|------|------|
| **LLM** | 看到数据样本 + 字段语义 + 分析目标 → 输出清洗操作列表（JSON） |
| **代码** | 接收 LLM 输出的操作列表 → 执行 winsorize/drop/fill → 生成清洗报告 |
| **Guardrails** | 校验 LLM 输出的操作列表（列名存在、操作合法、影响范围可接受） |

### 管道改进

```
用户查询 → 分析目标确认 → Scout（按目标识别相关字段 + 标注字段角色）
                              ↓
                        用户确认字段选择
                              ↓
                        Cleaner（LLM 基于字段角色 + 分析目标决定清洗策略）
                              ↓
                        用户确认清洗方案
                              ↓
                        Analyst（清洁数据上执行分析）
                              ↓
                        Reporter（按目标格式输出）
```

### 关键改动

1. **Cleaner prompt 注入分析目标**：让 LLM 知道用户要算均值还是建模型
2. **Cleaner prompt 注入字段角色**：目标变量（保守）vs 协变量（温和）vs 无关列（跳过）
3. **清洗策略 LLM 自主选择**：winsorize / drop / fill / 保留标注 / 跳过
4. **清洗理由用户可理解**：不用「IQR 1.5」，而用「该列 47 个值偏离正常业务范围」
