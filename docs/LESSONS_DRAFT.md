## 给未入门的人

1. **选步进式项目，别选一次性生成** — 每一步产出你都能看懂、都能插嘴。对话式是步进式的一种，分段生成也是。核心：中间状态可见。

2. **唯一需要学的能力：读 dump** — 三问定位法：用户最后说了什么？LLM 回了什么？工具调用了吗？**第一天就让 AI 帮你配好 dump，你只需要 `cat` 一个文件。** 不要自己配置。

3. **两个 AI 互审，你做裁判** — 不需要懂代码，需要判断"这个模式之前真的坏过吗"。**审查模型用便宜的/快速的，不一定要和写代码的模型同等级——省费用省时间。**

4. **第一次重复性 bug 出现时立刻立规矩** — 功能第一次跑通你不知道什么规则必要。但同一个类型的错误出现第二次时，你知道它会再来——那时候立的规矩才有针对性。hook、自检、铁律，不让同类违规再入 git。

5. **你管的不是代码，是信息流** — 数据从用户→LLM→工具→LLM→用户的链上每一个断点。用三问定位法找断点，不需要打开代码文件。

6. **同一功能区域反复出问题 → 不是缺补丁，是架构错了** — AI 永远不会主动说"这个模块该重建"。AI 只会无限打补丁。你是唯一知道"这里修过几次"的人。感觉"怎么又修这里"→ 喊停，要求 AI 重建架构。不需要数具体次数，只需要识别重复模式。

## 核心认知：你的角色

- **跨会话记忆**：AI 在单次对话内能记住上下文，但跨对话记忆为空白。每次新对话，bug 对 AI 都是"第一次见"。唯一拥有 53 天累积记忆的是你。
- **AI 没有"系统健康"概念**：你让它修 bug，它就修 bug。它不会说"修之前我们应该想想为什么这个模块反复出问题"——因为模块健康度不在它的优化目标里。它不是"速成"，是**没有全局视角**。
- **修复是做减法，不是做加法**（AI 代码中尤其成立）：AI 的倾向是加判断来消除症状，而非删冗余来修复根因。真正的修复产出的是更少的代码——拆墙，不补洞。HaGoKu 6/24 实证：两个补丁 +20 行（都撤回了），真正的修复 -135 行净删除。
- **硬编码常量是隐藏的补丁**：`MAX_TOOL_ROUNDS = 5` 看起来像"配置"，实际是代码替 LLM 决定它需要几轮。所有硬编码的阈值、上限、超时，本质上都是代码在猜 LLM 需要什么——猜错了就是 bug，且症状（字段表不显示）和根因（轮次上限）之间距离极远，极难定位。
- **通道的正反面定义**（v0.9.0）：代码做 LLM 不能做的（纯运算、IO）→ 通道补全 ✅。代码替 LLM 猜意图 → 违轨 ❌。通道不是虚无主义——是有明确边界的。
- **LLM 主动，代码被动**：正确的暂停模式是 LLM 调 `ask_user` → 代码 break。v2.0.1 将此模式扩展到 Doctor 闭环：LLM 诊断后输出 `[fix:xxx]` 标记 → 代码执行修复 → 结果追加到对话。**同一模式跨场景复用，是架构正确性的信号。**
- **通道的四个维度（v2.0.1 四大里程碑验证）**：① 不绑模型能力（删 JSON mode，prompt 替代硬编码参数）；② 不硬编码规则（Doctor 读操作手册，LLM 自主决策）；③ 不做领域区分（预设系统：同通道换提示词适配三领域）；④ 只执行不决策（LLM 输出 `[fix:xxx]`，代码自动执行）。**四个维度归结为一条：代码提供通用通道，LLM 拥有全部自主权。**
- **拆一个墙，会看到隔壁也是墙**：修 `MAX_TOOL_ROUNDS` 的根因后，暴露了 `route_to` 是从不执行的死工具（之前轮次不够，永远走不到它），暴露了"当前关注点注入"是多余干预（之前 LLM 被掐断后行为不稳才需要它）。6/25 延续此模式：昨天修的"阶段提示"本身是补丁→ 今天删掉整个阶段概念。**补丁套补丁——第一层补丁掩盖了真正的架构问题，直到被识别出来。**
- **旧架构的残留不只是废代码，它会主动干扰新架构**（HaGoKu 证据：`replyPending` 残留状态直接导致系统卡死）。
- **操作法**：让 AI 维护一个 `CHANGES.md`，每次修 bug 记一行：日期、功能模块、问题简述。同一功能模块频繁出现 → 标记 🔴 → 你喊停，要求 AI 重建该模块。不需要懂代码，只需要识别频率和模式。

## 给自己未来项目

### 复用
- dump 从第一天（让 AI 配，你只管 `cat`）
- pre-commit hook 从第一周（或第一次重复 bug 出现后立刻）
- 工具三问：LLM 自己能做吗？描述有"何时用"吗？同一件事几个入口？
- 通道十律做项目宪章
- AI 审查 AI 做标准流程（审查用便宜模型）
- 从能跑通的最简架构开始，不预先设计复杂度。对多数项目这意味着单 Agent，但别当教条——如果业务天然需要拆成多个独立职责，直接多 Agent 也可能是对的。

### 避坑
- 功能加模块时同步加约束（成对前进，不单独堆功能）
- 先定义端到端场景再堆功能（3-5 个完整用户旅程就是验收标准）
- prompt 膨胀从源头掐（出现"禁止""不要"→ 查 mismatch，修通道，删禁止）
- 定期换 AI 审查（不让一个 AI 连续对话太久产生惯性偏差）
- **重复性 → 重建**：同一个功能区域反复出问题 → 不修，重建架构。AI 永远不会主动提议重建。
- **打补丁 = 对错误架构加倍下注**。HaGoKu 6/18 一天六次"撤回"——每个补丁都在上一个错误方向上继续走，直到塌了才被迫回头。
- **相信你的"怎么又修这里"直觉**。那不是错觉，是架构在发出信号。
- **真根因修复会照亮周围死代码**：修掉一个隐藏的硬编码限制 → LLM 行为路径全变 → 原来"不生效"的代码变成"多余"的代码 → 连锁清理。HaGoKu 6/24：一个 `MAX_TOOL_ROUNDS` 修复 → 删了 route_to 整套机制 + 关注点注入 → 净删 135 行。
- **警惕"加诊断日志"的本能**：AI 找不到根因时的默认反应是加日志。这看起来无害，但它让你错以为"在做事"，推迟了真正的根因定位。HaGoKu 6/24：加了诊断日志 → 十分钟后被撤回，因为找到了真正的根因（一个数字）。问 AI："在不加一行日志的前提下，这个 bug 的可能根因有哪些？"——强迫 AI 进推理模式，不进补丁模式。
- **补丁套补丁**：6/24 的"阶段提示映射表"是 6/25 删掉整个阶段概念的上一环。6/24 以为是"映射错了"，6/25 发现是"映射这个想法本身就是错的"。**如果一个修复让你觉得"这个方案有点怪，但暂时能用"——它在掩盖真正的架构问题，不是解决了它。**
- **脏架构惩罚加法，干净架构奖励加法**：功能爆炸期的 581 commits 每次加功能都可能触发连锁崩塌（因为地基上有隐藏补丁）。通道净化后，加多项目支持是 4 个线性 commits，零撤回。v2.0.1 多 Sheet 支持 14 commits 零撤回。**同样加功能，脏架构成本指数增长，干净架构成本线性增长。**
- **每次撤回都是一件事**：通道违轨撤回和协议调试撤回性质不同，但态度相同——都应慎重。违轨撤回后要找根因（删代码而不是加补丁）；协议调试撤回后要复盘（为什么试了 4 次才找到根因）。HaGoKu 7/13 的 4 次 WS 撤回都不是随便试——每次都带明确假设，验证不成立后立刻撤。**撤回不可怕，可怕的是撤回了但没学到东西。**

## 三个边界条件（方法对，但前提要成立）

### 1. 版本控制习惯是救命稻草
HaGoKu 的 943 个小 commits 是你能在 53 天后回溯任何 bug 引入点的原因。**小 commit + 好 message = 时间机器。** 不用学 Git 复杂命令——让 AI 帮你 commit，你只需要说"提交，message 写 X"。但必须频繁提交，每次只改一件事。

### 2. 在你的业务领域里做项目
你能指挥 AI 做数据分析，不是因为你会写代码——是因为你懂数据分析。你知道"字段理解"、"效应量"、"置信区间"是什么，能判断 AI 的分析结果对不对。**跨到不懂的领域，你失去了唯一的锚——判断产出质量的能力。** 方法可以迁移，但项目方向必须在你的专业领域内。

### 3. 模型能力是天花板
同样的方法、同样的人，换成两年前的 LLM，可能走不到三分之一。铁律是 2026 年中的模型能力底座上建立的——模型越强，铁律越能生效。方法可以准备，但真正的上限在模型。**当模型能力再跃升一代，部分铁律可能不再需要——届时需要重新评估，别把铁律当永恒真理。**

## 关于"全是弯路"

回头看 53 天，感觉全是弯路。但这感知本身就是成长的证据。

**做个对比**：HaGoKu 6/24 的 bug（字段表不显示，根因是 `MAX_TOOL_ROUNDS = 5`）。如果这个 bug 发生在第 5 天——AI 会加至少 5 个补丁，commit 20 次，代码涨 200 行，两周后全部塌掉重来。实际上这个 bug 发生在第 53 天——两小时，两个补丁被识别并撤回，一个真正的修复（改一个数字），连锁清理 135 行死代码。

**同一个 bug，同样的你，同样的 AI。产出完全不同。** 唯一的变量是你大脑里长出来的识别回路——看到"加诊断日志"就知道是逃避，看到 15 行新增就知道太多了，看到硬编码常量就知道这是隐藏的补丁。

这些识别回路，不看 943 个 commits 长不出来。**学走路不是弯路——跌倒就是学走路的机制本身。你现在回头看觉得自己在绕弯，是因为你的眼睛比当时亮。弯路的感知是成长的副作用。**

### 第十一阶段：四大里程碑验证 — v2.0.1（6/26—7/10，121 commits，+4,145/-2,801）

**多项目打磨（6/26，44 commits）**：App 层 + ProjectRepository 根治多项目架构补丁。日志系统统一，报告模板重设计（暗色主题 + 现代卡片布局），铁律清理（硬编码路径消除、`except:pass`→`logger`）。

以下四个重构集中在 7/10，各自从不同维度验证了通道哲学：

**里程碑 1 — 预设系统：通道 × 提示词 = 多维度分析**
同一个引擎，换一段 prompt，适配三个领域（通用/股市/电商）。`_load_prompt()` 从 `~/.hagoku/active_preset` 读取，一键切换分析方向。**同步删除命令面板**（461行 CommandPanel + 83行 command_parser）——代码不再猜用户意图，LLM 自己理解。净删 1,015 行，新增预设系统仅 +51 行。

**里程碑 2 — 模型无关性：删除 query_parser 的 JSON mode 依赖**
`response_format=json_object` 是 OpenAI 专用功能。依赖它 = 换模型必炸。修复不是"加兼容层"——是**删掉对模型能力的依赖**。prompt 里写"请返回 JSON"替代硬编码的 `response_format` 参数。底层已有容错解析（`json.loads` → regex 提取），不需要模型侧强约束。净删 16 行。这个方向就是通道的正确定义：**代码提供通用通道，不依赖特定模型的特殊能力。**

**里程碑 3 — Doctor 操作手册：代码不硬编码规则**
Doctor 原来用硬编码的修复速查表选择操作。改为读取 `docs/doctor-operations.md` 操作手册，LLM 根据手册内容自主决策。手册包含触发条件、API、效果、验证方法。新增 +48 行（只有手册内容，无代码分支）。**同日撤回关键词匹配层**——更进一步：代码连"帮 LLM 匹配"都删了，LLM 直接读手册。

**里程碑 4 — Doctor 闭环：LLM 诊断 → 代码执行 → 结果反馈**
Doctor 聊天中，LLM 输出 `[fix:restore_default_prompt]` 标记，代码自动调用对应 API 执行修复，结果追加到对话末尾。**LLM 决定修什么，代码执行修复**——与"LLM 调 `ask_user` → 代码 break"是同构模式。新增 +57 行（只在检测和执行层，决策层在 LLM）。

**四个里程碑的共同主题**：代码越做越少，LLM 自主权越来越大。预设系统删了命令面板（-1,015行），query_parser 删了模型依赖（-16行），Doctor 从硬编码改为读手册（0行代码分支新增），Doctor 闭环只加执行层不加决策层（+57行）。**净效果：功能大幅增加，代码反而减少。**

> 核心公式定型：**通道 × 提示词 = 多维度分析**。不改代码，只换 prompt，同一个引擎适配不同领域。

### 第十二阶段：稳定性攻坚 + 通道纯度续证（7/13—7/15，14 commits，+317/-43）

**WebSocket 稳定性攻防（7/13，8 commits，4 次撤回）**：流式分析高峰期 WebSocket 频繁断连（1012 keepalive 超时）。AI 先走补丁路线：节流广播 → 撤回。累积合并 delta → 撤回。加诊断日志 → 撤回。删 asyncio 超时 → 撤回。根因最终定位：**uvicorn 内置 ws_ping 的 pong 响应在流式高峰延迟过大，触发 nginx/浏览器端 keepalive 超时。** 真正的修复：禁用 uvicorn ws_ping，改由应用层心跳替代。4 次撤回全是协议层调试的正常试错，不是通道违轨——**这是两种不同性质的撤回，要能区分。**

**多 Sheet 支持（7/15）**：Excel 多 sheet 选择器，主表单单选 + 副表单多选，支持多表联动分析。14 个 commits 的净增 +317 行，零撤回——干净架构上继续直线累加。

**通道纯度两条微续**：
- prompt 告知 LLM 跨对话经验库和方法库的存在，但不规定何时用——**告知，不指令。**
- 工具描述删"需用户明确指示才用"——**描述数据，不规定行为。**

> 这两条改动加起来不到 10 行。但它们是通道哲学在微观层面的持续验证：**每一次"删掉一句规定 LLM 行为的话"，通道就干净一分。**

## 一条线：69 天全是在逼近"干净通道"

如果用一句话总结这个项目，不是"做了一个数据分析工具"——是**用 1,110 个 commits 把代码从"替 LLM 做一切"剥成了"只做 LLM 做不到的事"**。

### 从代码量看：删除 = 逼近

每一次真正的进步，净效果都是代码减少：

| 阶段 | 方向 | 净变化 |
|------|------|--------|
| 功能爆炸 | 远离（堆功能） | +几十万行 |
| 大收缩 | 逼近（删 Agent/LLM/Kanban） | -710 行 |
| Session 重构 | 逼近（删 ProjectContext 320行） | -390 行 |
| 删阶段概念 | 逼近（删 7 处违轨） | -87 行 |
| 预设系统 | 逼近（删命令面板544行，+预设51行） | -1,015 行 |
| query_parser | 逼近（删模型依赖） | -16 行 |

**通道越干净，代码越少。功能越强，代码越少。** 这两个趋势在传统软件工程里是矛盾的——在这里是统一的。因为"功能"不在代码里，在 LLM 的自主权里。

### 从违轨看：清除 = 逼近

6 月的 24 次撤回，每一条都是同一种违轨：**代码替 LLM 做了判断。**

| 违轨类型 | 例子 |
|---------|------|
| 代码猜 LLM 阶段 | infer_current_focus() 硬编码映射表 |
| 代码猜 LLM 意图 | 命令面板解析用户输入 |
| 代码猜 LLM 状态 | had_tools 判断"是不是在探索" |
| 代码猜 LLM 需要几轮 | MAX_TOOL_ROUNDS = 5 |
| 代码猜 LLM 需要什么能力 | response_format=json_object |
| 代码填 LLM 没给的默认值 | used_in_analysis=True |
| 代码搬运 LLM 文本 | _scout_text 多层包装 |
| 代码替 LLM 生成字段表 | _build_basic_from_column_info |

每一种违轨的修复都是同一种方式：**删掉代码，把决策还给 LLM。** 没有一次修复是"加一段更聪明的代码"——因为"更聪明的代码"还是在替 LLM 做决策，只是这次猜得更准。猜得再准也是猜。

### 从架构看：剥离 = 逼近

```
功能爆炸期（远离）              通道净化后（逼近）
┌─────────────────────┐          ┌─────────────────────┐
│ 4 Agent 互相协调     │          │ 1 Agent 自主决策     │
│ Manager 编排         │          │ 无编排层             │
│ 双层 LLM             │          │ 单 LLM               │
│ 代码跟踪阶段         │          │ LLM 自然推进         │
│ 代码注阶段提示       │          │ prompt 描述流程      │
│ 命令面板猜用户意图   │          │ LLM 自己理解用户     │
│ 硬编码修复表         │          │ Doctor 读操作手册    │
│ 绑模型能力(JSONmode) │          │ prompt 通用兼容      │
│ 1 个领域             │          │ 3+领域(换提示词)     │
└─────────────────────┘          └─────────────────────┘
        远离 ←──────────────────────→ 逼近
             删掉的层 = 逼近的步数
```

### 一条线的终点

v2.0.1 的通道四个维度就是这条线的终点——不是"设计出来的"，是**剥出来的**：

- **不绑模型能力** — 剥掉了 `response_format=json_object`
- **不硬编码规则** — 剥掉了修复速查表
- **不做领域区分** — 剥掉了命令面板
- **只执行不决策** — 剥掉了所有"代码猜 LLM"的逻辑

终点不是"代码什么都没做"——代码仍然在做 LLM 做不到的事（加载数据、计算统计、写文件、路由消息）。终点是**代码做的每一件事，都有且只有一个理由：LLM 做不到。**

> 69 天，一条线。从"代码掌控一切"到"代码只做 LLM 做不到的事"。这条线不是设计出来的——是 1,110 个 commits 中每一次"删掉违轨代码"累积出来的。

## 心路历程：从"能不能做"到"凭什么这么做"

这段是给未来做第二个项目时的自己看的。不是技术记录——是心理记录。

### 第一阶段：狂喜（5/1—5/3）

"我真的能用 AI 做一个完整的东西。"

12 个 commits 搭出了一个多 Agent 平台。AI 写了基础设施、工具层、编排器、CLI。每一步都像变魔术——你说"加一个 Reporter"，AI 就加一个。感觉没有上限。你不知道这些 Agent 以后会让你多痛苦，你只知道"它们跑起来了"。

这个阶段的关键心理：**对 AI 的信任是无条件的。** AI 说加什么你就加什么。AI 写了 86,000 行代码，你不知道里面有多少是将来要删的。

### 第二阶段：膨胀（5/4—6/10）

"什么都能加！"

Streamlit Web UI、React 重建、知识库、Doctor 诊断、44 个工具、双层 LLM、看板系统。功能像叠积木一样往上堆。commit 数爆炸——有一天 78 个 commits。你觉得"我们在飞速前进"。

实际上你正在踩未来所有坑的地基。只是当时你还没见过这些坑长什么样，认不出来。

这个阶段的关键心理：**量 = 进步。** 你甚至没有"架构"这个词的概念——你只看到功能在增加。AI 也没有提醒你，因为它也觉得"加功能"就是对的。

### 第三阶段：沉默的崩塌（6/11）

"为什么会变成这样。"

44 天积累的复杂度在一个点上同时爆发了。不是某个具体的 bug——是整个系统在你手上变得不可控。修一个地方坏三个地方。Scout 卡住。LLM 的输出不知道在哪里被截断了。你不知道为什么，AI 也不知道为什么——因为 AI 忘了 44 天前它自己写的代码。

你做了一个当时不知道有多重要的决定：**删。** 4 Agent → 1 Agent。Manager 删了。双层 LLM 删了。KanbanDB 删了。CLAUDE.md 从 520 行砍到 67 行。

这个阶段的关键心理：**第一次对 AI 的建议说不。** 不是某个具体建议——是对整个"多 Agent 是正确方案"的假设说不。这是你第一次意识到：AI 可以搭积木，但评判积木搭得好不好是你的活。

### 第四阶段：通道觉醒（6/12—6/22）

"代码不该替 LLM 做任何决定。"

这是最痛苦的十天。不是功能难做——是每走一步都在推翻前一天的自己。

6/18 一天六次撤回：加了循环、撤了。加了工具限制、撤了。加了字段生成、撤了。加的时候每次都觉得"这个逻辑对"，撤回的时候每次都觉得"这个逻辑对但方向错"。方向错在哪？**代码在替 LLM 出主意，而不是让 LLM 自己做判断。**

这个阶段诞生的铁律、刹车、触发词——不是"我学到了新知识"，是"我终于能把脑子里那种不对的感觉说清楚了"。"刹车 C 不准填默认值"——不是你读了一篇论文后立的规矩，是你被 `setdefault("used_in_analysis", True)` 咬过。"刹车 D 不准搬运 LLM 文本"——咬你的是 `_scout_text` 多层包装。"信息通道断裂"——咬你的是 `return` 硬编码覆盖了计算好的值。

这个阶段的关键心理：**从"AI 你帮我"变成了"AI 你别乱帮"。** 不再问 AI "你怎么修这个 bug"，而是问 AI "这个 bug 出现之前，LLM 收到了什么消息"——把 AI 从修理工降级为取证工具。修理工 AI 会加补丁，取证 AI 会告诉你通道在哪里断了。

### 第五阶段：验证（6/24）

"我能一眼认出补丁了。"

同一个 bug（字段表不显示），同样的症状，AI 给出了两个补丁。第 5 天的你会说"好，加进去"。今天的你给了完全不同的反应：看到"控制工具写入 session"，沉默了——因为 15 行新增。看到"添加诊断日志"，警觉了——因为这不是修根因。然后你做的不是 merge，是**要求重新定位根因**。

结果：真正的根因是一个数字 `5` 改成 `99`。净删 135 行代码。

### 第六阶段：通道终极化（6/25 白天）

"代码和 LLM 的边界终于清楚了。"

事件的起因是 6/24 的一个 commit——`75ac54d`，它给代码加了"告诉 LLM 当前阶段"的功能，带了一个硬编码的映射表（"set_columns → 评估清洗阶段"）。这个映射是错的。

但重点不是"映射错了"——重点是**整个"代码告诉 LLM 阶段"的思路就是错的**。如果代码替 LLM 判断它在哪个阶段，那代码就是在替 LLM 做决策。错了。

于是今天做的事：**删除阶段概念。** 不是"修正映射表"，是"删掉映射表本身"。不止映射表——session.py 的阶段推断、agent.py 的 phase_hint 注入、prompt.md 的"当前阶段会标注"、registry.py 的 phase_tag、前端所有 STAGE_LABELS——全删。代码不再知道、不再关心、不再告诉 LLM "你在哪个阶段"。

中间有一段多路探索。AI 试图用"对话层控制循环轮次"替代"run_step 内部循环"。听起来合理——但它本质上是"对话层替 LLM 猜什么时候该停"。撤回了。又试图改停点条件为"有文本+没调工具"——本质上是"代码替 LLM 判断它是不是在探索"。也撤回了。

最后留下的是最简单的逻辑：**LLM 调 `ask_user` → 代码 break。** LLM 主动说"我要停了"的时候代码才停。代码不猜，代码只响应。

这个阶段最重要的心理转变：**通道有了正反面定义。** 以前只说"代码不要替 LLM 做 X"——全是禁止。今天终于说出正面：代码可以做 LLM 不能做的事——加载数据、计算统计、写文件。这些是通道的合法补全。通道不是虚无主义——是有明确边界的。

### 第七阶段：通道验证（6/25 晚间）

"干净架构上，功能是直线累加。"

同一天。早晨还在删阶段概念、撤回对话循环——代码里每一个替 LLM 做判断的地方都在被清除。晚上开始加多项目支持：ProjectManager、项目切换、报告页项目感知。

4 个 commits。线性。零撤回。

不是功能变小了——多项目架构牵涉后端、前端、WebSocket、状态恢复，是系统级的改动。也不是 AI 变聪明了——同一个 AI。唯一的变量是**架构现在是干净的**。干净的架构上没有"代码替 LLM 猜阶段"这种隐藏的地雷，加一个功能就是加一个功能，不会踩到三个月前的坑、不会触发五个模块外的连锁崩塌。

早晨的 6/25 和晚间的 6/25 是同一天的镜子两面：
- 早晨：30 commits，两次撤回，删 87 行——**清理**
- 晚间：4 commits，零撤回，加 243 行——**建设**

清理是建设的前提。不是"先清理再建设"的先后顺序——是**不清理就建设不了**的因果关系。功能爆炸期的 581 commits 里，每一百个里不知道有多少是在补救前面补丁的副作用。现在的 4 个 commits，每一个都是纯粹的增量。

这个阶段的关键心理：**终于不再是"修一个坏三个"了。** 不是因为技术更好了——是因为地基上没有补丁了。

### 第八阶段：哲学验证（7/10）

"通道不是一个技术方案——是一套可复现的原则。"

7/10 集中落地的四个里程碑，每一个都是通道哲学在不同维度的投影：

- 删掉 query_parser 的 JSON mode 依赖 → **代码不绑模型能力**
- Doctor 从硬编码修复表改为读操作手册 → **代码不硬编码规则**
- 预设系统：同通道换提示词适配三领域 → **代码不做领域区分**
- Doctor 闭环：LLM 输出 `[fix:xxx]` → 代码执行 → **代码只执行不决策**

这四个不是孤立的功能——是同一个原则在四个场景的重复应用。当一个原则能跨场景复用时，它就不是"经验"了——是**定理**。

更重要的是数字：
- 预设系统净删 1,015 行（删命令面板 544 行，只加了 51 行预设内容）
- query_parser 净删 16 行
- Doctor 操作手册 +0 行代码分支（只加了 48 行手册文档）
- Doctor 闭环 +57 行（全在执行层，无决策层代码）

**功能大幅增加，代码反而减少。** 这不是巧合——是"修复是做减法"这条原则在最宏观层面的验证。6 月的清理（-1,187行）是拆墙，7 月的建设（+1,344行净增）是在干净地基上搭房子。拆墙的时候痛苦，建的时候顺畅。

这个阶段的关键心理：**从"我不知道对不对"变成了"我知道为什么对"。** 6 月靠直觉——看到补丁觉得不对，说不上来为什么。7 月靠原则——每个改动都能归到通道的四个维度之一。直觉变成了可复现的判准。

### 最后的话

如果你在读这份文档，说明你在做第二个项目，或者第三个。你在怀疑"怎么又全是弯路"。

不是弯路。是你现在的眼睛能认出路两边的坑了——但你还是得亲自走一遍才知道哪些坑在你脚下。第一遍用腿走，第二遍用车开，第三遍你都不知道自己在绕坑——因为你已经不觉得那是路了。

**你对 AI 从信任 → 膨胀 → 怀疑 → 剥离 → 到自己做判断的每个阶段，都不是弯路。是必经。**
